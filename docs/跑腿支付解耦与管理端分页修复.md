# 跑腿支付解耦与管理端分页修复

> 关联：docs/社区跑腿模块设计方案.md、docs/跑腿信用与评价设计.md
> 模块：backend/twelvet-runner（Spring Boot 单体 twelvet-admin）
> 日期：2026-09-06

## 1. 背景与问题

1. **管理端任务列表失效**：`RunnerTaskServiceImpl.adminPage()` 旧实现注释"简化"，直接复用接单大厅
   查询 `selectHall(null,...)`——只返回 `pending` 且未过期的任务，`pageNum/pageSize/status/keyword`
   参数全部被忽略，`total` 恒等于当页行数，前端任务管理页（`ui/src/pages/Runner/admin/TaskPage.tsx`）
   的状态 Tab 过滤形同虚设。
2. **付费任务发布与支付创建强耦合**：`RunnerTaskController.publish()` 同步调
   `payOrderService.createPayOrder`，本地支付宝密钥无效时网关签名抛异常 → 整个发布请求 500，
   **任务未落库**，用户无法创建付费任务。
3. **无重新支付入口**：支付发起失败后任务卡在 `pay_status=unpaid`，"我发布的"列表没有再发起支付的入口。

## 2. 方案

### 2.1 管理端真分页

- `RunnerTaskMapper.xml` 新增 `selectAdminPage` / `countAdminPage`（共用 `<sql id="adminPageWhere">`）：
  - WHERE：`<if test="tenantId != null">tenant_id = #{tenantId}</if>`（与现有 mapper 租户处理一致，
    tenantId 取 `stateMachine.currentTid()`，租户开关关闭时查全平台）；
    `status` 精确匹配；`keyword` 对 `title / task_no / description` 模糊匹配（OR）。
  - `ORDER BY id DESC`，`LIMIT #{offset}, #{size}`；count 同条件 `SELECT COUNT(*)`。
- `RunnerTaskServiceImpl.adminPage()`：pageNum/pageSize 归一化（默认 1/20，pageSize 上限 200），
  offset=(pageNum-1)×pageSize，keyword/status 去空白后传空即不过滤，返回 `TableDataInfo.page(list, total)`。
- 前端 `TaskPage.tsx`：原有状态 Tab 传参 `status` 与后端一致；新增关键词搜索框
  （`Input.Search` → `keyword` 参数，`params={{ status, keyword }}` 触发 ProTable 刷新）。

### 2.2 付费发布与支付创建解耦

`RunnerTaskController.publish()`：

1. 任务先经 `taskService.publish()` 落库（status=pending、pay_status=unpaid，DB 默认值），事务先提交。
2. 支付创建移入 try/catch：成功 → `bindPayInfo` + 响应 `pay` 返回支付参数；
   失败 → 日志记录，响应 HTTP 200 携带 `pay: {error: "..."}`、`payMessage: "支付发起失败，
   请稍后在'我发布的'里重新支付"`，任务照常创建成功。

新增 `POST /runner/task/{id}/pay`（重新支付，幂等）：

1. 仅发布者本人可调用；免费任务/已 paid 任务直接幂等返回。
2. 已绑定支付单（`pay_out_trade_no` 非空）→ 先 `queryPayStatus`：
   - 已支付 → 同步任务 `pay_status='paid'`，返回 `alreadyPaid=true`；
   - 未支付或**网关查询异常**（本地密钥失效场景）→ **复用/返回原单**（`reused=true`），不重复下单；
   - 原单不存在（查询正常返回 null）→ 视为无可用支付单，走重新创建。
3. 重新创建：`createPayOrder` → `bindPayInfo` 绑定新支付单（`RunnerPaySuccessEventListener` 按
   `out_trade_no` 反查标记 paid 的逻辑无需改动，天然兼容）；失败 → HTTP 200 降级响应
   （`pay.error` + `payMessage`），任务保持可重试。

已知取舍：`createPayOrder` 先插 `trade_pay` 再调网关，网关失败会留下一条未绑定任务的 orphan 支付单
（无法被支付，无副作用）；重新支付绑定旧单后不再产生新单。

### 2.3 前端"我发布的"重新支付入口

`ui/src/pages/Runner/MyList.tsx`：操作列对 `isPaid===1 且 payStatus!=='paid'（未取消）` 的任务显示
**"去支付"** 按钮 → `POST /runner/task/{id}/pay`；按响应分支提示（已支付 / 复用原单 / 新支付单 /
发起失败），有 `payUrl/qrCode` 时新窗口打开。仅改动 MyList.tsx 与 admin/TaskPage.tsx 两个 UI 文件。

## 4. 验证记录（2026-09-06，本地 twelvet-admin 单 jar :8080，库 twelvet-fast）

造数：admin 发布 4 个任务并流转到不同状态（pending=13、completed=14、cancelled-after-assign=15、
accepted=16），付费任务发布降级产生 task 17（isPaid=1）；分页验证时库中任务共 13 条，
随后 4.2 的全新发布再产生 task 18（isPaid=1），共 14 条。

### 4.1 管理端分页

| 步骤 | 结果 |
|---|---|
| GET /runner/task/admin/page?pageNum=1&pageSize=100 | total=13 == DB `COUNT(*)`，返回全部状态（pending/accepted/completed/cancelled），不再只查 pending ✅ |
| ORDER BY id DESC | [18,17,16,15,14,13,10,...] 递减 ✅ |
| pageNum=1/2（pageSize=2） | 两页数据不重叠，total 稳定，第 2 页首行 = 全量第 3 条（offset 正确）✅ |
| status=pending / status=completed | total 分别 == DB 同状态 COUNT，且行内 status 全部一致 ✅ |
| keyword=KWPAGE7X（标题） | total=4，命中 4 条种子任务（跨 4 种状态）✅ |
| keyword=KWPAGE7X&status=completed | total=1 且 id=14 ✅ |
| keyword=RUN202609060023（task_no 前缀） | total=2 == DB `task_no LIKE` 计数（task 9+10）✅ |
| keyword="filter seed"（仅 description 含有） | total=1（task 13），证明 description 参与匹配 ✅ |
| keyword 无命中 | total=0 ✅ |

### 4.2 付费发布解耦与重新支付

| 步骤 | 结果 |
|---|---|
| POST /runner/task/publish（isPaid=1，本地支付宝密钥无效） | **HTTP 200**（旧版 500），`taskId=18` 落库，`status=pending`、`payStatus=unpaid`，`pay.error` 含网关签名异常信息，`payMessage` 提示去"我发布的"重新支付 ✅ |
