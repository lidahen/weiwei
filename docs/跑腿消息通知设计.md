## 一、目标

跑腿任务（twelvet-runner）状态流转时，自动通过 IM 站内消息通知交易对方，让发布者/跑腿人不刷大厅也能感知进度。要求：**通知失败不影响主流程事务**。

## 二、探索结论（技术选型依据）

- `twelvet-im-server` 已有可直接复用的进程内 service：`IImService#sendMessage(userId, peerId, productId, type, content)`（`ImServiceImpl`），内部完成 ensureConversation + 插入 `im_message` + 更新会话 lastMsg，消息 `type` 支持 `system`。**无需直接操作 ImMessageMapper，也无需新建 runner_notify 通知表以外的 IM 侧改动。**
- 部署形态是单 jar（twelvet-admin 聚合所有模块），runner-server 直接 Maven 依赖 `twelvet-im-server` 注入 `IImService` 即可，无跨服务调用成本。
- 项目已有 Spring 事件先例：payment 发 `PaySuccessEvent`，runner 的 `RunnerPaySuccessEventListener` 消费；`twelvet-framework-log` 的 `LogAutoConfiguration` 已 `@EnableAsync`。
- 租户上下文 `TenantContext` 是 ThreadLocal，`@Async` 线程取不到 → 事件必须携带 tenantId，监听器线程内显式 `TenantContext.set(tid)`（含 Quartz 扫描场景，任务表里有 tenant_id 可兜底）。

**选型：Spring 事件 + @Async @EventListener 监听器调 IImService.sendMessage。** 同步调用会把 IM 写库耦合进状态机事务且失败会回滚主流程；事件异步解耦且天然可扩展（后续加推送/短信多加监听器即可）。

## 三、通知触发点矩阵

| 状态变化 | 触发动作 | 通知谁 | 文案（type=system） |
|---|---|---|---|
| pending → accepted | 抢单成功（assign） | 发布者 | 【跑腿】您的任务「{title}」已被抢单，跑腿人正在准备接单 |
| accepted → running | 开始配送（start） | 发布者 | 【跑腿】任务「{title}」跑腿人已开始配送 |
| running → pending_confirm | 提交完成（finish） | 发布者 | 【跑腿】任务「{title}」跑腿人已提交完成，请确认验收 |
| accepted → pending（reject） | 跑腿人拒单 | 发布者 | 【跑腿】任务「{title}」跑腿人拒单，任务已重新放回大厅 |
| pending_confirm → completed | 确认完成（confirm） | 接单人 | 【跑腿】任务「{title}」已完成确认，感谢您的跑腿服务 |
| pending_confirm → refund | 申请退款 | 接单人 | 【跑腿】任务「{title}」下单人申请退款，客服将介入处理 |
| → cancelled（取消/超时） | 发布者取消 | 接单人（若有） | 【跑腿】任务「{title}」已被取消：{reason} |
| accepted → pending（reject）顺带 | — | （发布者已覆盖，同上） | — |

发送者取操作人 operatorId；接收人等于发送人时跳过；接单人为空时跳过（如 pending 直接取消）。

## 四、技术方案

```
状态机 RunnerTaskStateMachine（doAssign/doTransition/doTransitionWithTime/doCancel 成功后）
    └─ publishEvent(RunnerTaskNotifyEvent{taskId, action, operatorId, remark, tenantId})
                          │ （事务内发布，@Async 监听器线程异步执行）
                          ▼
RunnerTaskNotifyListener  @Async @EventListener，整体 try/catch：
    1. tenantId 缺失时用任务表 tenant_id 兜底，TenantContext.set(tid)（finally clear）
    2. taskMapper.selectById 反查任务 → 定位接收人（见矩阵）、组装文案
    3. IImService.sendMessage(operatorId, receiverId, null, "system", content)
    4. 落 twelve_runner_notify_log（status=sent/failed, error_msg）——审计与排查
```

### 失败降级策略

- 监听器全量 try/catch，任何异常只记 log.warn + notify_log 置 failed，**绝不向上抛**（@Async 本身也不影响主线程事务）。
- IM 发送失败或 notify_log 写失败互不影响（log 写包在独立 try/catch）。
- Quartz 超时扫描（无租户上下文）同样可用：事件 tenantId 为 null 时监听器用 task.tenantId 兜底。
- 通知是"尽力而为"：主流程状态机日志（twelve_runner_task_log）才是事实来源，大厅 logs 接口仍可查全量流转。

### 服务端未读闭环（2026-09-06 追加）

废弃 localStorage 本地已读口径（`im_bell_seen` / `im_bell_unread` 已删除），改用 `im_unread` 表服务端持久化已读位点，跨刷新 / 换设备 / 换 token 一致。

**未读判定口径**：会话内 `msg_id > 用户已读位点（im_unread.last_read_msg_id）` 的他人消息（撤回的不计）。`im_unread` 原有 `unread_count` 列保留为 sendMessage 同步维护的冗余计数（接收方递增、读后清零），不作为判定依据；判定以位点为准，天然自愈（漏计数不影响正确性）。

**接口（ImController，沿用 sa-token 登录校验 `StpUtil.getLoginIdAsLong()`，无菜单权限项）**

| 接口 | 说明 |
|---|---|
| `GET /im/unread/count` | 未读汇总：`{total, convs:[{convId, unread}]}`（convs 仅含有未读的会话，供铃铛下拉红点） |
| `PUT /im/unread/read?conversationId=&messageId=` | 标记已读：`messageId` 可选（读到哪条，超出会话最后一条会被截断，位点只进不退），缺省推进到会话最后一条；`conversationId` 缺省=全部会话已读；返回 `{convId?, total}`（标记后剩余未读，前端免二次轮询） |

**数据改造**（DDL 已同步 `backend/data/neighborswap.sql` 的 `im_unread` 建表语句并在库上执行）：

- `im_unread` 增加 `last_read_msg_id bigint NOT NULL DEFAULT 0`（已读位点）；
- 存量会话按 `last_msg_id` 初始化双方位点（历史消息视为已读，避免上线即未读爆炸）；
- `conv_id` 全局唯一（im_conversation 主键），`im_unread` 不加租户列，统计时经 `im_conversation.tenant_id` 过滤，口径与 `/im/conversation/list` 一致。

**写入时机**（均在 `ImServiceImpl.sendMessage` 同一事务内，runner system 通知同路径覆盖）：接收方 `INSERT IGNORE` 兜底建行 + `unread_count+1`；发送者清零并把位点推进到本条消息（自己发的永远不算未读）。读接口为"INSERT IGNORE 兜底 + UPDATE 推进位点/清零"两段式幂等写，不依赖 ON DUPLICATE KEY 的版本语法。
