## 1. 意图与为什么

weiwei 已经具备二手交易、交换、动态、互助、IM、AI、推荐、后台与多租户能力，但产品层面存在一个结构性矛盾：**能力很宽，信任交易链很窄**。

- 买家付款后卖家如何拿到钱没有闭环；
- 信用分散在商品 / 换物 / 互助三个域；
- 售后规则不一致；
- 本地密度没有被产品化。

结果是一个「功能演示很完整、真实交易不敢用」的平台。

本文件把产品从「功能集合」收敛为「可信的本地交易平台」：先补齐资金与信任底座，再用 AI 降低供给摩擦，最后用社区生态做复购与密度。所有取舍以「单个社区能否跑通交易」为判断标准。

> **Phase 1「真实交易闭环」的准确含义**：本地环境 + 种子/模拟数据的试点，验收看状态机、账本与 E2E，不涉及真实资金与真实居民。真实资金试点是后续独立门槛，需先解决合规与商户资质（见 §14）。

### 2.2 关键缺口（按严重度）

#### G1 资金未闭环（P0，最严重）

- `PaySettleDTO` 注释明确「当前支付服务暂未实现自动结算，后续可接入分账 / 转账 API」（`twelvet-payment-api/.../PaySettleDTO.java:6-8`）。
- `IPaymentGateway` 只有创建 / 查询 / 退款 / 验签，没有结算或打款能力（`twelvet-payment-api/.../IPaymentGateway.java`）。
- 全库没有卖家余额、结算单、打款记录服务；`trade_withdraw` 只有表（`docs/db/twelvet-fast_2026-10-21.sql:3076`），后台 `pendingWithdraws` 指标永远为 0（`AdminMarketplaceMapper.xml:222`）。
- 后果：买家付款进入平台商户号，卖家只能线下收款；平台无法担保，也无法在纠纷时扣回。

#### G2 信用分散（P0/P1）

- 商品卖家有信用分公式（`UserProfileServiceImpl.java:100-160`，新人默认 80，扣分含退款 / 纠纷 / 超时）。
- 换物、互助各自维护信用口径；没有跨域账户、没有统一处罚、没有统一对外展示。
- 后果：同一用户在三个域可能是三种信用；买家无法在商品详情快速判断卖家是否可信。

#### G3 售后规则不一致（P1）

- 当前 `seller_agreed` 后买家 7 天寄回窗口按 `create_time`（申请时间）扫描，卖家拖 48h 会压缩买家窗口（退款 spec §8.3）。
- `done` 后 7 天申请资格窗口已按 `done_at` 计算（这部分是对的）。
- 已发货 / 已收货订单允许「仅退款」，但原因未按状态收紧、凭证未强制，存在「留货拿钱」风险。
- 部分退款仍把整单 / 整支付单置 `refunded`（退款 spec §14 简化），财务口径需接受。
- 后果：规则对买家不透明，对卖家不公平，运营裁决缺依据。

#### G4 供给摩擦（P1）

- 发布页已接 `assistProductCopy/Image/Recognition/Valuation` 四个 AI 接口（`ui/src/pages/marketplace/ProductPublish.tsx:3-6`），但没有整合成「拍照 → 识别 → 文案 → 估价 → 发布」的一屏流程；用户仍需多次点击与填写。
- 后果：闲置卖家（低频、怕麻烦）流失，供给密度起不来。

#### G5 本地密度未产品化（P1）

- 商品只有 `location` / `city` 文本字段（`Product.java:42-44`）；DB 虽有 `lat/lng` 列（`docs/db/...sql:1382-1383`），但 Java 实体未映射、发布页无采集。
- 推荐以兴趣 / 热度 / 向量为主，不是「先近后远」。
- 后果：同城二手最核心的「近」没有变成产品能力，物流与面交成本高。

#### G6 运营工具缺口（P1）

- 退款通知目前主要覆盖买家，卖家 / 运营缺触达；订单状态变化没有统一通知中心。
- 纠纷台缺 SLA 与超时提醒；资金看板缺结算 / 提现口径。
- 后果：运营靠人工巡检，规模一上来就崩。

#### G7 功能维护面过宽（P2）

- AI 音乐 / 视频 / 语音克隆、复杂推荐实验等与核心交易无关，持续消耗维护成本。
- 后果：核心链路投入不足。

## 3. 定位与用户

### 3.1 一句话定位

**C 端：3 公里内，敢买敢卖的邻里二手集市。**
**B 端：给社区 / 园区一套能跑起来的闲置交易与邻里服务系统。**

不做全城分类信息，不做纯社区论坛，不做 AI 功能集合。

### 3.2 用户与 JTBD

| 角色 | 核心任务（JTBD） | 当前卡点 | 产品回应 |
|---|---|---|---|
| 买家（住户 / 园区员工） | 就近买到便宜可信的闲置，出问题能退 | 卖家可信度不可见；售后规则不清 | 卖家卡片、担保交易、售后矩阵 |
| 卖家（同一批人） | 3 分钟挂出闲置，卖出后拿到钱 | 发布步骤多；收款靠线下 | AI 发布助手、自动结算 / 提现 |
| 社区运营方 | 提升活跃、多一个服务抓手 | 缺运营方价值闭环 | 租户版看板、社区活动工具 |
| 平台运营 | 审核、纠纷、风控 | 缺 SLA、缺资金工具 | 纠纷台、结算 / 提现审核、风控规则 |

**关键洞察**：买卖双方是同一批人，**供给端体验决定密度**。卖家不来，买家没东西买；卖家拿不到钱，就不会再来。产品投入优先供给端与信任，而不是继续加买家侧功能。

### 3.3 楔子（Wedge）与「社区」的定义

先做透一个场景：**同小区 / 同园区的闲置面交**。它同时满足高频、近距离、低物流成本、可当面验货，是建立信任与密度最短的路径。快递发货作为补充，不作为第一阶段主场景。

**社区 = 租户（`sys_tenant`）**。Phase 0–1 不新增 `community_id` 实体：

- `sys_tenant` 的种子数据本身就是 `default-community / thu-community / pku-community`（`docs/db/...sql:2540`）；
- 用户、商品、订单已按 `tenant_id` 隔离；商品表已有 `tenant_id`；
- 跨租户的「3 公里」浏览会破坏租户隔离，Phase 3 之前不做；Phase 3 若要做，需要租户显式开启 + 隐私评审。
- 「社区认证」在 Phase 1 降级为「社区成员」徽章 = 已登录 + 属于该租户（`sys_user.tenant_id`）；不做物业名单/地址核验。

## 4. 目标 / 非目标 / 反目标

### 4.1 目标（90 天 = Phase 0–2）

1. 一个试点租户（社区）跑通「发布 → 支付 → 面交 / 发货 → 确认 → 结算 → 提现」全闭环（mock 资金），无线下转账。
2. 售后规则统一为一张矩阵，买家 / 卖家 / 运营三方都能按规则预期。
3. 商品详情展示统一卖家信用卡片；信用事件有跨域账本，但 Phase 1 不改域内资格。
4. 发布流程整合为「拍照 → AI 草稿 → 估价 → 发布」，目标 <60 秒。
5. 建立核心漏斗埋点与试点社区看板。

### 4.2 非目标（本期不做）

- 真实资金渠道接入（Phase 0–1 保持 mock；真实接入需合规方案）。
- 真实居民参与的试点（Phase 1 是本地模拟试点；真实试点需另立门槛）。
- 全城扩张、跨城市运营、跨租户 3 公里浏览。
- 原生 App / 微信小程序（先 H5 验证）。
- 自助式多租户 SaaS 销售页（先手工签 1–3 个试点）。
- 佣金 / 租户版定价的最终确定（Phase 4 前）。
- 按商品行拆分退款（整单部分退即可）。
- 第三方 KYC / 实名认证服务（Phase 1 运营人工核验）。
- AI 音乐 / 视频 / 语音克隆的新增投入（冻结）。

### 4.3 反目标（做到这些算失败）

- 平台担保变成空话：买家付款后卖家仍需线下收款。
- 纠纷裁决后钱没退 / 退错，产生资损。
- 卖家能在已发货后「留货拿钱」。
- 信用分可以靠刷单 / 刷好评操纵。
- 试点社区周成交靠补贴，补贴停则归零。
- 多租户隔离被新功能破坏（所有 SQL 保持 `<if test="tenantId != null">`）。
- 为了 AI 而 AI：新增无法对应交易指标的生成功能。

## 5. 战略取舍（我做的决定）

| # | 决定 | 理由 | 影响 |
|---|---|---|---|
| D1 | 技术多租户，运营先单社区 | 密度是二手交易的第一性原理；多租户是交付形态，不是增长策略 | 不建自助 SaaS；试点社区手工运营 |
| D2 | 先担保 / 结算，再谈佣金 | 没有资金闭环，佣金无从谈起 | Phase 1 做 mock 结算与账本 |
| D3 | 区分两个 7 天：`done` 后 7 天是**申请资格**（已正确）；`seller_agreed` 后 7 天是**寄回窗口**（需修） | 两个计时器不能混；卖家拖延不应压缩买家寄回时间 | 新增 `seller_agreed_at`，扫描从它起算 |
| D4 | 已发货后的仅退款**不自动通过**，必须卖家同意或平台介入；`done` 的仅退款限定原因 + 强制举证 | 防「留货拿钱」；现有流程已无自动同意，缺的是原因/凭证收紧 | 改 `validateApply` 与前端文案 |
| D5 | AI 只投供给与售后效率 | 这两处直接对应发布耗时与运营成本 | 冻结与交易无关的生成能力 |
| D6 | 渠道先 H5，不投原生 App / 小程序 | 本地验证期，复用现有 Umi | 不新增端 |
| D7 | 北极星 = 单社区周完成交易数 | 防止全城 GMV / DAU 虚假繁荣 | 所有看板按租户切片 |
| D8 | 社区 = 租户，Phase 0–1 不新增 `community_id` | 现有 `sys_tenant` 就是社区；跨租户浏览破坏隔离 | 事件、看板、商品筛选统一用 `tenant_id` |
| D9 | 结算在 `done_at + 7 天` 售后窗口结束后才发生（T+1 打款） | 避免卖家在买家保护期内提现，Phase 1 不需要平台垫付 | `hold_until = done_at + 7d`，窗口内退款走原路 |
| D10 | Phase 1 不做第三方 KYC；运营人工核验卖家实名与收款账户 | 本地模拟试点，第三方 KYC 会拖垮 6 周排期 | 提现前置人工审核；发布不强制实名 |
| D11 | 面交用服务端校验的 6 位面交码，买家输码即确认收货；自提单不做自动确认 | 现有 `self_pickup` 仍走快递发货逻辑，无法闭环；自动确认会让未见面订单被放款 | 复用 `trade_pickup_code`，`delivery_type='self_pickup'` |
| D12 | Phase 1 信用只做「展示合并 + 事件账本」，不改域内资格 | 三套公式已经存在，强行融合会引入回归 | 卖家卡片展示商品域分数；跨域事件仅记录 |
| D13 | Phase 1 不采集卖家精确坐标；距离排序留到 Phase 3 | 精确住址是隐私/安全风险；DB 的 `lat/lng` 暂不映射 | 商品按租户筛选；Phase 3 用租户中心点 |

## 8. 关键机制设计

### 8.1 担保交易与结算（P0）

#### 8.1.1 目标状态机

```
买家支付成功
   │
   ▼
settlement_order: holding（担保中，资金不结算）
   │
   ├── 退款成功（holding 内）──> cancelled（资金原路退回）
   │
   └── 订单 done（确认收货/自动确认/面交码确认）
          │
          ▼
     等待售后窗口：hold_until = done_at + 7 天
          │
          ▼
     pending_settle（窗口结束，T+1）
          │
          ▼
     settled（已结算到卖家余额）
          │
          ├── 提现申请 ──> withdraw pending ──运营审核──> passed/rejected
          │
          └── 售后退款（已结算）──> clawback（余额扣回/人工）
```

#### 8.1.2 数据模型（Phase 1 mock）

- `seller_account`：`user_id`、`tenant_id`、`status`、`real_name`、`id_no_masked`、`payout_channel`（bank/alipay）、`payout_account`、`available_balance`、`frozen_balance`、`version`。唯一键 `(user_id, tenant_id)`；余额按租户隔离，不跨租户共享。
- `settlement_order`：`settlement_id`、`tenant_id`、`pay_no`、`order_id`、`seller_id`、`amount`、`commission`、`status`、`hold_until`、`settled_at`。
- `seller_balance_flow`：`flow_id`、`tenant_id`、`user_id`、`biz_type`（settle/refund/withdraw/clawback）、`biz_id`、`amount`、`direction`、`balance_after`、`create_time`。**必须可审计、不可改。**
- `trade_withdraw`：复用现有表（`withdraw_id/user_id/amount/bank_name/bank_card_no/status`），补 `tenant_id`、`payout_channel`、`payout_account`、`third_no`、`audit_cs_id`、`audit_time`、`fail_reason`。Phase 1 以现有银行卡字段为权威；支付宝账号作为后续扩展。

#### 8.1.3 规则

- 结算对象：仅商品订单（`trade_order`）。互助 / 换物 / 租户续费各自结算，不共用本账本。
- 结算金额：实付金额 − 退款金额 − 佣金（Phase 1 佣金 = 0）。
- **结算时点**：`done` 后进入 7 天售后窗口；窗口结束且无进行中退款，T+1 结算到卖家余额。`hold_until = done_at + 7d`。
- 退款优先级：窗口内退款从担保资金原路退（此时尚未结算）；结算后退款从卖家余额扣回，不足则冻结后续结算并转人工。**Phase 1 不做平台垫付**；若出现余额不足，订单进人工队列，不计为自动完成。
- 提现：Phase 1 运营人工审核（mock 打款）；Phase 2 接真实渠道。
- 对账：每日 `settlement_order` + `seller_balance_flow` + `trade_pay` 三方对账；差异进人工队列。
- 租户：三张新表都带 `tenant_id`；定时任务无租户上下文时显式传 `null`（全租户语义），与现有退款任务一致。

#### 8.1.4 合规与实名

- 平台代收代付存在「二清」风险。真实上线前必须由合规 / 法务确认路径，优先使用支付宝「担保交易 / 分账」或微信「电商收付通」等持牌产品，避免资金沉淀在平台自有账户。
- 本地开发阶段只做 mock 账本与状态机，不接真实资金；接口按合规路径预留（`IPaymentGateway` 增加 `settle` / `payout` 能力或在独立 `ISettlementGateway` 中实现）。
- Phase 1 实名：运营人工核验（卖家提交姓名 + 证件号，后台只存掩码 + 审核结论）；**不接第三方 KYC**。发布不强制实名；提现必须实名 + 收款账户已审核。
- Phase 1 提现走银行卡（现有 `trade_withdraw.bank_name/bank_card_no`）；支付宝账号字段预留但不启用。

### 8.2 统一信用（P0/P1）

#### 8.2.1 现状

- 商品域已有 `creditProfile`：`base = avgScore × 20`（无评价默认 80），`creditScore = round(base × (0.7 + 0.3 × completionRate)) − 5 × penalizedCount30d`，扣分含退款 / 纠纷 / 超时，等级 90/80/60 分档。
- 换物、互助各有信用逻辑；无跨域账户。

#### 8.2.2 Phase 1 设计（展示统一 + 事件账本，不改域内资格）

- 新增 `user_credit` 汇总表：`user_id`、`tenant_id`、`score`、`level`、`goods_score`、`exchange_score`、`runner_score`、`updated_at`。
- **域分数仍是权威**：商品域沿用现有公式作为 `goods_score`；换物 / 互助分数由各自服务上报。`user_credit.score` 只是展示用汇总值。
- 汇总规则：按各域「已完成单数」加权平均；没有数据的域不参与；全部无数据时默认 80（新人保护）。商品详情卖家卡片优先展示 `goods_score`（当前场景相关），个人主页展示汇总等级。
- 新增 `credit_event`：`event_id`、`tenant_id`、`user_id`、`domain`（goods/exchange/runner/content）、`event_type`（completed/refund/dispute_lost/overdue/report_upheld）、`biz_id`、`delta`、`create_time`。**Phase 1 只做审计账本，不用 `delta` 重算域分数**，避免与现有实时公式重复扣分。
- 跨域生效的范围：Phase 1 只影响「个人主页的汇总等级」，**不影响换物/互助的最低信用门槛**；门槛仍取各自域分数。Phase 2 再评估跨域资格。
- 对外只暴露「信用等级 + 完成单数 + 好评率 + 平均响应 + 纠纷败诉次数」，不暴露原始分与算法细节。
- 商品详情「卖家卡片」字段：头像 / 昵称、社区成员徽章（租户归属）、信用等级、完成单数、好评率、平均响应时长、加入时间。

#### 8.2.3 防操纵

- 只有 `done` 订单计入完成单数；退款 / 关闭订单不计。
- 评价必须来自真实订单；同一买家对同一卖家 30 天内只计一次。
- Phase 1 只做订单/评价去重 + 人工抽检；**设备指纹、支付账号关联、异常低价识别放 Phase 2**。
- 信用申诉：卖家可对扣分发起申诉，运营裁决后修正 `credit_event`（留审计日志）。

### 8.3 售后策略矩阵（P1）

| 订单状态 | 仅退款 | 退货退款 | 申请资格窗口 | 寄回/处理规则 |
|---|---|---|---|---|
| 未发货（`unshipped`/`paid`） | ✅ 即时 | ❌ | 支付后至发货前 | 卖家 48h 未处理 → **自动同意并退款**（订单仍为未发货） |
| 已发货未确认（`shipped`） | ⚠️ 需卖家同意或平台介入，**不自动通过** | ✅ | 发货后至自动确认前 | 卖家同意后 7 天内寄回（从 `seller_agreed_at` 起算） |
| 已确认收货 7 天内（`done`） | ⚠️ 仅「未收到 / 描述不符 / 损坏」，**需 ≥1 张凭证** | ✅ | `done_at + 7 天`（已正确） | 卖家同意后 7 天内寄回（从 `seller_agreed_at` 起算） |
| 已确认收货超 7 天 | ❌ | ❌ | — | 仅平台介入（人工） |

**规则变更（相对当前实现）**

1. **寄回窗口**：新增 `seller_agreed_at`，扫描从它起算，不再用 `create_time`；`done` 的申请资格窗口保持 `done_at` 不变。
2. **未发货 48h 自动同意**：`pending_seller` + 订单 `unshipped/paid` + 类型 `refund_only` → 超时自动退款；其余情况 48h 升级 `mediation`（保持现状）。规则需在申请页明示「卖家超时将自动退款」。
3. **已发货仅退款不自动通过**：现有流程已经全部走 `pending_seller`，无自动同意路径；本次补的是原因/凭证约束，不是新增状态。
4. **done 仅退款收紧**：只允许 `not_received/not_as_described/damaged/wrong_item`，且至少 1 张凭证；`no_longer_needed/other` 在 done 仅退款下禁用。
5. **退货运费**：Phase 1 只做规则展示与运营口径，不做自动结算/报销（无运费金额字段）；Phase 2 再补字段与报销流程。
6. 退款成功后订单置 `refunded`；部分退款同样置 `refunded`（本期简化，财务口径接受）。

**售后文案要求**

- 申请页明确展示「当前订单状态可用的售后类型 + 时限 + 谁承担运费 + 卖家超时后果」。
- 订单详情入口根据 `refundByOrder.canApply/activeRefundId/denyReason` 展示，不展示不可用按钮。
- 后端需在 `checkApply` 返回 `orderStatus` 与 `allowedTypes`，前端据此过滤类型选项，而不是前端猜。

### 8.4 AI 发布助手（P1）

#### 8.4.1 目标流程

```
拍照（1–9 张）
  → 识别：品类 / 成色 / 品牌 / 关键属性
  → 生成：标题（3 个备选）+ 描述 + 标签
  → 估价：参考价区间 + 建议价
  → 用户确认 / 微调
  → 选社区 / 面交点
  → 发布
```

目标：3 步内、60 秒内完成；AI 失败可降级为手工填写，不阻塞发布。

#### 8.4.2 复用现有能力

- 前端已有 `assistProductCopy`、`assistProductImage`、`assistProductRecognition`、`assistProductValuation`（`ProductPublish.tsx:3-6`）。
- 后端经 Java BFF 转发到 `ai-service`，不新增前端直连。
- Phase 1 只做流程整合与埋点，不重训模型；识别 / 估价准确率用人工抽检评估。

#### 8.4.3 度量

- 发布耗时中位数、AI 草稿采纳率、发布成功率、发布后 48h 首询率、AI 单均成本。

### 8.5 本地密度与面交（P1）

#### 8.5.1 社区与距离

- Phase 0–2：社区 = 租户；商品列表 / 详情 / 事件 / 看板全部用 `tenant_id`；不做跨租户浏览。
- Phase 1 不采集卖家精确坐标；DB 的 `product.lat/lng` 暂不映射。
- Phase 3 再做距离：以租户中心点（`sys_tenant` 新增 `lat/lng` 或独立 `community_profile`）计算「距社区中心」，不暴露卖家精确住址；是否跨租户由租户显式开启 + 隐私评审。

#### 8.5.2 面交流程（Phase 1）

- 下单时 `delivery_type='self_pickup'`（`trade_order` 已有该列）；**必须线上支付**，不支持货到付款。
- 支付成功后，卖家在订单详情点「生成面交码」：
  - 复用 `trade_pickup_code` 表（`order_id/code/expire_at/used`）；
  - 订单置 `shipped`，`shipped_at=now`，`auto_confirm_at=NULL`；
  - 自动确认任务跳过 `delivery_type='self_pickup'`。
- 面交时买家输入卖家出示的 6 位码；服务端校验 `order_id + code + used=0 + expire_at > now`，通过后：
  - 面交码置 `used=1`；
  - 订单置 `done`，`done_at=now`；
  - 商品标记已售；
  - 进入 7 天售后窗口，之后结算。
- 买家不确认 / 卖家不放码：订单停在 `shipped`，**不自动放款**；超过 7 天进入运营队列，由运营联系双方或按证据裁决。
- 爽约：买家可在面交码使用前按售后规则申请退款；卖家可上报爽约，运营记录信用事件。
- 说明：换物面交码目前仅双方核对、服务端不校验；商品面交**不能直接复用其实现**，只复用表与交互形态。

## 9. 路线图

> 90 天 = Phase 0（2 周）+ Phase 1（6 周）+ Phase 2（6 周），约 14 周。Phase 3–4 是 90 天后的方向，不在本轮实现计划内；每个 Phase 单独出 plan。

### Phase 0 — 收口（2 周）

**目标**：把已经做的做对，建立度量。

- 修完退款评审遗留 6 项：参数 400、缺参 loading、类型按订单状态过滤、退货物流非空、`trade_refund` 索引、`scanTimeouts` 事务。
- 通知中心 v0：退款 / 订单状态变化覆盖买家 + 卖家 + 运营（站内 + IM 系统消息）。
- 运营纠纷台：SLA 倒计时、超时提醒、批量筛选。
- 核心漏斗埋点 + 试点社区看板 v0。
- 产出《担保交易与结算》合规 / 产品方案（本文件 §8.1 细化到可开发）。
- 验收：全部测试通过；退款全链路 E2E 再次通过；看板能看到 Phase 0 事件。

### Phase 1 — 信任底座（第 3–8 周）

**目标**：试点租户（本地模拟）交易闭环，无线下转账。

- mock 结算：`seller_account`、`settlement_order`、`seller_balance_flow`、提现审核（人工实名核验 + 银行卡）。
- 跑通「支付 → 快递发货 / 面交 → 确认 → 7 天窗口 → 结算 → 提现」；窗口内退款走原路，窗口后退款走余额扣回。
- 统一信用卡片 v1 + 商品详情卖家卡片（展示商品域分数 + 社区成员徽章）。
- 售后策略矩阵落地（后端校验 + 文案 + 运营台），含未发货 48h 自动同意、done 仅退款举证。
- 面交流程 v1（`trade_pickup_code` 服务端校验，自提单不自动确认）。
- 验收：1 个试点租户；100% 交易走平台状态机；结算账本与支付流水日对账一致；纠纷率 <2%。

### Phase 2 — AI 供给（第 9–14 周）

**目标**：供给端摩擦显著下降。

- AI 发布助手整合为一屏；识别 / 估价 / 文案采纳率埋点。
- AI 售后分诊：自动识别退款类型 / 要件 / 责任方，减少运营介入。
- 风控规则 v1：高频退款、异常低价、关联账号、站外引流关键词。
- 验收：发布 <60s；AI 辅助发布 >50%；人工纠纷介入率下降 30%。

### Phase 3 — 密度与复购（90 天后，第 15–24 周）

**目标**：试点社区自持增长。

- 本地推荐：租户中心距离 / 新鲜度 / 信用加权；不暴露卖家精确坐标。
- 动态与商品联动；换物 / 互助作为拉新与留存钩子。
- 社区运营工具：活动报名、跳蚤市场、种子供给导入。
- 验收：30 日复购 >20%；周完成交易 100+；自然新增供给占比 >50%。

### Phase 4 — 商业化（Phase 1–3 指标健康后）

- 交易佣金（先试点，公开费率）。
- 租户版授权（物业 / 园区 / 校园）。
- 置顶 / 推广（克制，避免伤害信任）。
- 不在指标健康前做自助 SaaS 销售页。

## 10. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| 冷启动密度不足 | 最可能失败 | 单社区打透；活动 + 种子供给；不投广告 |
| 支付二清合规 | 上线阻断 | 优先持牌渠道担保 / 分账；本地 mock；法务确认 |
| 站外交易 | 平台无收入、无保障 | 担保、信用、售后、面交码把交易留在站内 |
| 小社区口碑放大 | 一次欺诈毁社区 | 实名 / 社区成员、首单小额兜底、快速仲裁、黑名单 |
| 信用刷分 | 信任体系失效 | 真实订单、去重、风控规则、申诉审计 |
| 功能维护面过宽 | 核心投入不足 | 冻结非核心 AI 生成；季度砍功能 |
| 多租户隔离破坏 | 数据泄露 | 所有新 SQL 保持 `<if test="tenantId != null">`；E2E 加跨租户用例 |
| AI 成本 / 质量波动 | 体验与毛利 | 降级手工流程；按单成本监控；人工抽检 |
| 面交爽约 / 不放码 | 体验与纠纷 | 不自动确认；7 天进运营队列；信用事件 |
| 卖家窗口内提现 | 资损 | 结算等 7 天窗口结束；窗口内退款走原路 |
