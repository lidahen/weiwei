# 交换广场二期设计：向量智能匹配 + 漏斗看板 + 换物信用

> 版本：v1.0（待评审后实施）
> 日期：2026-10-25
> 前置：一期已完成并验证（见 [交换广场模块设计方案.md](交换广场模块设计方案.md)，commit 20c4b94/b1b5f1f）
> 本期目标：解决以物换物的核心矛盾——**双重需求巧合**。路径：漏斗看清瓶颈 → 向量双向匹配让"对的人看到对的物" → 信用分守住履约达成率。
> 实施范围：ai-service 新增匹配服务与路由、Java exchange 模块接入、前端三处入口、1 张新表、2 个新 Job。

---

## 一、总体方案

```
【供给侧索引】(每租户)                        【需求侧索引】(每租户)
 onswap 物品文本向量                           want_desc+want_cats 文本向量
 title+description+类目+成色                    （物品主人隐含的需求）
        │                                            │
        └──────────── FAISS IndexFlatIP（L2 归一化，内积=余弦，镜像 product_vector） ────────────┘
                          │                                        │
      ┌───────────────────┘                                        └──────────────────┐
      ▼ 正向召回                                                                        ▼ 反向召回
"我的需求向量" ↔ 供给索引                                                    "我的物品供给向量" ↔ 需求索引
 → Square 页「为你推荐」                                                     → 详情页「可能想换 TA 的人」
                                                                            → 每日推送「有人想换你的物品」（IM）
```

三条能力与既有代码的镜像关系（全部已核实存在）：

| 本期能力 | 镜像的既有实现 | 说明 |
|---|---|---|
| 向量索引与召回 | `ai-service/app/services/product_vector.py`（272 行） | 每租户 `data/faiss_indexes/product_t{tid}.faiss+.meta.json+.npy`、`diff_rows` 增量、`asyncio.Lock`、`ProductVectorUnavailable` 降级——整体克隆，换成两条索引（supply/demand） |
| embedding | `ai-service/app/services/embedding_service.py` | SiliconFlow BAAI/bge-m3（OpenAI 兼容 API），`embed_texts/embed_query` 直接复用，不新增模型配置 |
| Java 调用客户端 | `twelvet-product/.../client/RecommendVectorClient.java` | `getForData/postForData` + 超时 + 503 降级；exchange 侧镜像为 `ExchangeMatchClient`（复用 `aiGuideWebClient` WebClient 配置，同 `ExchangeAiModerationClient` 的用法） |
| 定时推送链路 | `RecommendServiceImpl.scanPriceDrop()`（770-790 行） | Quartz 行按 `tenant_id` 分组 → `selectSenderUserId(tid)` 系统发送人 → `IImService.sendMessage`；推送去重用快照表 diff（同"收藏价格快照"思路） |
| 信用分 | `RunnerReviewServiceImpl.creditProfile()`（124-160 行） | **实时计算、无独立表**：`creditScore = clamp(0,100, round(base*(0.7+0.3*completionRate30d)) - 5*penalizedCount30d))`；exchange 用 order_log 违约动作 + 评价分做同构数据源 |

## 二、数据库变更（仅 1 张新表 + 2 个 Job）

### 表：`twelve_exchange_match_push`（匹配推送去重快照）

```sql
CREATE TABLE IF NOT EXISTS `twelve_exchange_match_push` (
  `id`             BIGINT      NOT NULL AUTO_INCREMENT,
  `tenant_id`      BIGINT      NOT NULL,
  `item_id`        BIGINT      NOT NULL COMMENT '物品ID',
  `pushed_user_ids VARCHAR(1000) NOT NULL DEFAULT '[]' COMMENT '已推送过的需求方 userId（JSON 数组，diff 去重）',
  `last_push_time` DATETIME    DEFAULT NULL,
  `create_time`    DATETIME    DEFAULT CURRENT_TIMESTAMP,
  `update_time`    DATETIME    DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_item` (`tenant_id`, `item_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='换物匹配推送去重快照';
```

> 脚本：`backend/sql/exchange_match.sql`（含 sys_job 124/125 两条 INSERT，默认暂停同库内惯例）。

### Job（124/125，invoke_target 与 bean 方法一一对应）

| job_id | invoke_target | cron（建议） | 逻辑 |
|---|---|---|---|
| 124 | `exchangeMatchTask.syncVectors` | `0 */30 * * * ?` | 调 Python `/exchange-match/reindex` 增量同步双索引（镜像 `productRecommend.syncVectors`） |
| 125 | `exchangeTask.scanMatchPush` | `0 0 10 * * ?`（每日 10 点） | 反向匹配扫描 + 快照 diff + IM 推送（镜像 `productRecommend.scanPriceDrop` 的租户分组/系统发送人模式） |

## 三、ai-service 侧设计

### 3.1 新服务 `app/services/exchange_vector.py`

克隆 `product_vector.py` 的骨架（类名 `ExchangeVectorService`、模块级单例 `service`、`ExchangeVectorUnavailable` 异常），差异点：

- **双索引**：`_paths(tenant_id)` 返回两套文件：`exswap_supply_t{tid}.faiss/.meta.json/.npy` 与 `exswap_demand_t{tid}.*`（复用 `settings.faiss_index_path` 目录）。索引读写/增量逻辑相同，封装成内部通用方法后实例化两份（或一个类持有两组索引）。
- **数据源**：直读 MySQL `twelve_exchange_item WHERE status='onswap'`（字段 id/tenant_id/title/description/cat_l1/cat_l2/condition_level/want_desc/want_cats/accept_any/update_time），SQL 写法镜像 `_fetch_onsale`。
- **文本构造**：
  - 供给文本 `supply_text(row)`：`title + 类目中文名(product_category_dict) + 成色 + description`（镜像 `product_text` 的拼接思路）；
  - 需求文本 `demand_text(row)`：`want_desc + want_cats 对应类目中文名`；`want_desc` 为空且 `want_cats` 为空 → 不进需求索引（无有效需求语义）。
- **类目名映射**：启动时（或首次使用时）读一次 `product_category_dict` 做内存缓存（code→name），错误容忍（查不到用 code 本身）。
- **公开方法**：
  - `reindex_all() / reindex(tenant_id) -> int`（增量 diff，同 product_vector）
  - `match_for_demand(tenant_id, user_texts: List[str], limit) -> hits`：用户多条需求文本取均值向量（镜像 `candidates` 的均值逻辑）↔ 供给索引
  - `match_wanters(tenant_id, item_id, limit) -> hits`：物品供给向量 ↔ 需求索引（返回 demand 侧 item_id，即"谁的需求指向我的物品"，再由 Java 反查物品→owner）
  - 注意：FAISS 索引存的是 item_id（不是 user_id），双向都用 item 做主键——"想换我的人"= 需求命中物品的 owner，Java 侧 JOIN 反查。

### 3.2 新路由 `app/routers/exchange_match.py`

镜像 `recommend.py` 的全部惯例（`ApiResponse`、503 降级、`tenant_id_from_request`、不计 `ai_usage_daily` 配额——同款理由：服务端内部批任务与展示依赖）：

| 端点 | 方法 | 入参 | 返回 | 说明 |
|---|---|---|---|---|
| `/exchange-match/reindex` | POST | body `{tenant_id?: int}` | `{indexed: int}` | 增量同步双索引（Job 124 调用） |
| `/exchange-match/for-me` | POST | body `{want_texts: List[str], limit}` + `X-Tenant-Id` 头 | `{hits: [{itemId, score}]}` | 我的	want_desc 集合 ↔ 供给索引（Square 推荐位） |
| `/exchange-match/wanters` | GET | `?item_id=&limit=` + `X-Tenant-Id` 头 | `{hits: [{itemId, score}]}` | 该物品 ↔ 需求索引（详情页 + 推送扫描） |

注册进 `app/main.py`（或路由汇总处，以现有注册方式为准）。

### 3.3 降级语义（与 recommend 一致）

embedding 未配置 / 索引未构建 / SiliconFlow 不可用 → `code=503`，Java 侧降级：推荐位返回空列表、详情页隐藏区块、推送扫描跳过本轮。**任何匹配失败都不阻塞主流程。**

## 四、Java 侧设计（twelvet-exchange）

### 4.1 新客户端 `client/ExchangeMatchClient.java`

镜像 `RecommendVectorClient`（WebClient 注入方式同 `ExchangeAiModerationClient` 已用的 `aiGuideWebClient`）：
- `List<Map<String,Object>> forMe(List<String> wantTexts, int limit)` → POST `/exchange-match/for-me`（透传 X-Tenant-Id）
- `List<Map<String,Object>> wanters(Long itemId, int limit)` → GET `/exchange-match/wanters`
- `int reindex()` → POST `/exchange-match/reindex`（长超时，镜像 REINDEX_TIMEOUT）
- 503/超时/异常 → 返回空或 0，由调用方降级（**不抛异常**）

### 4.2 C 端接口（ExchangeSquareController / ExchangeItemController 扩展）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/exchange/square/recommend?limit=8` | 登录用户：取其所有 onswap 物品的 want_desc → `forMe` 召回 → 批量查物品卡片（过滤已下架/锁定）→ 无命中或降级返回空数组。权限 `@SaCheckLogin` |
| GET | `/exchange/item/{id}/wanters?limit=6` | 物品主人或任何登录用户可看：`wanters` 召回 → JOIN 反查需求物品及其 owner（昵称/换物主页摘要），降级返回空数组 |

> wanters 返回的 itemId 是"需求侧物品"（别人的 onswap 物品），映射到人 = 该物品 owner，正好点击可跳对方物品详情，形成"以物找人"闭环。

### 4.3 定时任务

- **`task/ExchangeMatchTask.java`**（`@Component("exchangeMatchTask")`）：`syncVectors()` 调 `matchClient.reindex()`，日志记 indexed 数；失败仅 warn（下轮重试）。
- **`ExchangeQuartzTask.scanMatchPush()`**（挂在既有 `exchangeTask` bean 下，Job 125）：
  1. 分页扫全租户 onswap 物品（`selectOnswapAll` 全局扫描，**不写 tenantId `<if>`**——沿用二期修复结论）；
  2. 逐物品 `wanters(itemId, 3)` → 取 owner 不等于物品主人的命中（排除自我需求）；
  3. 与 `twelve_exchange_match_push.pushed_user_ids` diff，只推**新出现**的需求方；
  4. 按行内 `tenant_id` 分组取系统发送人（镜像 scanPriceDrop），`IImService` 推送文案：`【换物】有人想用「{对方物品标题}」换您的「{我的物品标题}」，去看看 → /exchange/detail/{itemId}`；
  5. 更新快照（upsert，冲突更新 pushed_user_ids/last_push_time）；单物品失败 try/catch 跳过不炸整批。
  6. 频控：快照表天然去重"同一个人对同一物品只推一次"；整体每日一轮。

### 4.4 信用分（镜像 runner，实时计算，无新表）

- `ExchangeReviewServiceImpl.creditProfile(Long userId)`：新增 mapper 聚合 SQL（数据源全在库内）：
  - `completionRate30d`：近 30 天该用户参与订单的 completed 占比（twelve_exchange_order，owner_a/owner_b 双视角）
  - `penalizedCount30d`（**按动作归因方式分两类统计**，因 order_log.operator_id 对系统动作记 0、对裁决记管理员，直接按 operator 统计会漏）：
    - 用户直接违约：`action IN ('cancel','dispute') AND operator_id = #{userId}`
    - 系统判定违约（双方各计一次的近似）：`action IN ('timeout','admin_force_cancel')` 且订单参与方含该用户（order_log JOIN twelve_exchange_order ON owner_a_id/owner_b_id = userId）
    - MVP 近似口径（记录在案）：timeout 不区分是哪方拖的、admin_force_cancel 不区分责任方，双方各计一次；精细化留三期
  - `base`：其收到的好评均分 ×20（review.score 均值 1-5 → 20-100），无评价默认 70
  - `creditScore = clamp(0,100, round(base*(0.7+0.3*completionRate30d)) - 5*penalizedCount30d)`（与 runner 公式逐字一致）
- 暴露端点：`GET /exchange/credit/{userId}`（`@SaCheckLogin`，返回 `{creditScore, completedOrders30d, penalizedCount30d, avgScore}`）；详情页 owner 摘要（`detail()`）增加 `ownerCredit` 字段。
- **门槛拦截**：`ExchangeOfferServiceImpl.create()` 增加 `creditScore < 40` 拒绝发起（常量 `MIN_CREDIT_TO_OFFER = 40`，注释注明二期可配置化）。
- 未登录/新用户无数据 → 默认 70 分（base 默认值兜底），不误伤新人。

## 六、冷启动与降级策略

| 场景 | 行为 |
|---|---|
| SiliconFlow embedding 未配置/欠费 | 503 → 全部入口静默降级（推荐位隐藏、推送跳过），主流程零影响 |
| 租户换物池 < 20 件（向量召回意义小） | `forMe` 结果不足 4 条时降级为**类目热门填充**（复用 selectSquarePage 按 hot_score，按用户 want_cats 过滤） |
| 用户未填 want_desc/want_cats | forMe 无输入 → 空结果 → 推荐位隐藏；发布页一期已有字段，配合运营引导 |
| FAISS 索引损坏 | reindex 全量重建（product_vector 同款：meta 校验失败即重建） |

## 七、验证方案（沿用一期标准）

1. **编译门禁**：`mvn -f backend/pom.xml compile -pl :twelvet-exchange-server -am`（注意 `-pl` 用冒号 artifactId 形式）；前端 `npm --prefix ui run tsc` + `max build`。
2. **Python 语法**：`python -m py_compile` 两个新文件 + ai-service 可启动（`uvicorn` 冒烟或现有启动方式）。
3. **运行时 E2E**（前置自审事实：`ai-service/.env` 已有 EMBEDDING/SILICONFLOW 配置，但 `data/faiss_indexes/` 下**从无 product_t* 索引**——本地向量链路从未实际跑通过，不能假设可用）：
   - 启 ai-service（8001）→ `POST /recommend/reindex`（现有商品索引）做 embedding 前置冒烟：
     - **成功**（返回 indexed>0）→ 说明 SiliconFlow key 有效，继续本模块正向用例；
     - **503/0** → key 无效或欠费：本期 E2E 改为验证**降级链路**（推荐位隐藏/wanters 空数组/推送跳过、主流程零 ERROR、日志 warn 可见），并在交付报告标注"匹配正向用例待 key 可用后补跑"；不阻塞其余验收；
   - 正向用例：造 2-3 件 want_desc 语义相关的物品（如"想换键盘"/"出键盘"）→ 手动 `POST /exchange-match/reindex` → 校验 `data/faiss_indexes/exswap_*` 文件生成 → `forMe`/`wanters` 互相命中且 score 有区分度；
   - 触发 Job 125（`/job/cron/run`，job_id=125）→ 校验 `twelve_exchange_match_push` 快照落库 + IM 消息生成 + 二次触发不重复推；
   - 信用分：`GET /exchange/credit/{alice}` 返回合理分数；低信用账号（造违约数据）发起意向被 40 拒绝；
   - 全程应用日志零 ERROR（降级 warn 除外），`sys_job_log` 成功记录。
4. **回归**：一期 E2E 主链路（发布→审核→意向→建单→双确认→评价）不回退。
