# 交换广场模块设计方案（以物换物）

> 版本：v1.0（草案，待评审）
> 日期：2026-10-25
> 模块位置：`backend/twelvet-exchange`（新建 Maven 模块，聚合进 twelvet-admin 单进程部署）
> 参照先例：跑腿互助（`twelvet-runner`）全链路落地方式
> 配套复用：AI 初审（`/ai/moderation/content`）、AI 估价（`/ai/assist/*`）、IM（`IImService`）、面交码（参照 `trade_pickup_code`）、类目字典（`product_category_dict`）

---

## 一、整体业务流程

```
【A】发布换物物品          【B】浏览广场 / 收到匹配推荐
      │（含"想换什么"）              │
      ▼                              ▼
   AI 初审 ──驳回──> 通知修改    看中 A 的物品 X
      │通过                           │
      ▼                              ▼
  物品上架(onswap)              发起换物意向 offer
      │                        （选出自己物品 Y + 留言 ±补差价）
      ▼                              │
      ├────────── IM 通知 A ──────────┘
      ▼
 A 查看收到的意向列表，接受其中一条
      │（事务：offer→accepted，X/Y 物品→locked，其余 pending offer 自动婉拒）
      ▼
 生成交换订单（双边履约）
      │
      ├── 面交模式：线下约见，各自出示交换码 → 各自点"已交付" → 各自点"已收到"
      └── 快递模式：各自填运单号 → 各自点"已收到"
      ▼
 双方都确认 → 订单 completed，物品 X/Y → swapped（换出下架）
      ▼
 双向评价（换物信用积累）
```

**与跑腿/买卖的本质差异**：跑腿是**单边履行**（跑腿人履行、下单人确认），换物是**双边履行**——双方各自交付、各自确认，订单状态机必须建模双边进度。这是本模块状态机设计的核心点。

---

## 二、技术架构决策

| 方案 | 说明 | 结论 |
|------|------|------|
| **A. 新建 `twelvet-exchange` 独立模块** | 仿 twelvet-runner 三段式（聚合 pom + api + server），自带表、状态机、控制器 | ✅ 采用 |
| B. 扩展 `twelvet-product`（加"可交换"标记） | 复用商品发布/审核/搜索，但 `product` 与价格交易强耦合（price 必填、onsale/sold 流转、库存、运费），换物物品无售价、多出"期望换物"字段、生命周期不同 | 不采用，回归成熟核心表风险大于新建成本 |

**决策**：走方案 A。可共享的部分**直接引用而非复制**：

- 类目字典 `product_category_dict`（code/parent_code/level），换物物品直接用同一套类目编码
- AI 初审流水表 `ai_moderation_log`（表本身通用，新增 `bizType='exchange_item'`）
- IM 通知：进程内依赖 `twelvet-im-server`，调 `IImService.sendMessage(userId, peerId, productId, "system", content)`（与 runner 相同）
- 面交码：参照 `trade_pickup_code` 结构新建 `twelve_exchange_pickup_code`（一单两码，双方各出示一个）
- 支付（**仅二期差价补偿场景**）：依赖 `twelvet-payment-api` 的 `IPayOrderService` + `PaySuccessEvent`，不碰 twelvet-trade

## 三、数据库表设计

> 命名沿用 `twelve_` 品牌前缀；所有表带 `tenant_id`，索引一律 `(tenant_id, ...)` 复合开头（对齐 runner 范式）；mapper 显式传 `tenantId`，不走自动租户拦截器。


**物品状态机：**

```
draft（草稿，可选支持）→ auditing（AI 初审+人工兜底，同商品流）
auditing → onswap（初审 low 风险自动过 / 人工 pass）
auditing → rejected（初审 high 自动驳 / 人工 reject，IM 通知主人）
onswap → locked（某个 offer 被接受，进入订单，不可再收意向）
locked → onswap（订单取消/被裁决取消，物品解锁回广场）
locked → swapped（订单 completed，换出下架）
onswap → offshelf（主人主动下架，可重新上架回 onswap）
```

**订单状态机（双边履行）：**

```
created（订单建立，双方物品 locked）
   ↓ 任一方标记"我已交付"（面交现场点按钮 / 快递填单号）
delivering（部分交付）
   ↓ 双方都已标记交付
pending_confirm（等双方各自确认收到）
   ↓ 双方都已确认
completed（双方物品 → swapped）

异常分支：
created/delivering → cancelled
   · 双方都未交付：任一方可直接取消，物品解锁回 onswap
   · 单方已交付：取消需走纠纷由后台裁决（防"交付后反悔白嫖"）
delivering/pending_confirm → disputed（任一方发起，物品保持 locked，等后台裁决）
disputed → completed（裁决完成，后台 force-complete）
disputed → cancelled（裁决取消，后台 force-cancel，物品解锁）
超时：订单建立 7 天未进入 pending_confirm → 自动 cancelled + 通知；
      pending_confirm 超 3 天未双确认 → 视为默认收货自动完成（对齐跑腿自动确认惯例）
```

> "A 交付 / B 交付 / A 确认 / B 确认"是四个独立时间戳列，`status` 由状态机根据四个列的填充情况推进，避免引入子状态爆炸。确认动作与本人交付解耦（面交时双方同时在场依次点击即可）。

## 四、核心业务逻辑

### 1. 发布与审核（复用商品 AI 初审链路）

- 发布即 `status='auditing'`；生成 `item_no = ESC + yyyyMMddHHmmss + 6位随机`
- **AI 初审**：新建 `ExchangeAiModerationTask`（`@Component("exchangeAiModeration")`，方法 `auditItems()`），扫 `status='auditing'` 的物品，调 `${ai.service.url}/ai/moderation/content`（WebClient，Header 带 `X-Tenant-Id`），结论写 `ai_moderation_log`（`bizType='exchange_item'`）：
  - low → 自动过，`onswap`，填 `publish_time`
  - high → 自动驳，`rejected` + `IImService` 通知主人
  - medium → 留人工（后台 `/admin/exchange/item` 待审列表）
- sys_job 注册 `exchangeAiModeration.auditItems`（每 10 分钟，对齐商品初审任务节奏）
- **AI 估价参考**（纯展示）：详情页"估价参考"按钮调已有 `/ai/assist` 估价能力，辅助双方判断交换是否等值；不落库、不参与流转

### 2. 发起意向（offer）

- B 在物品 X 详情页发起：从**自己的 onswap 物品**中选一件 Y，或快速文字描述（`offer_snapshot`）；附留言 `message`、可选 `diff_amount`
- 校验：不能对自己的物品发起意向；同一物品同一人仅一个 pending；被锁定/下架物品不可发起
- IM 通知 A："您的物品《X》收到一条换物意向"
- 意向 72h 未处理自动 `expired`（定时任务）

### 3. 接受意向（核心并发点，乐观锁）

一个事务内三步原子操作（任一步影响行数为 0 即回滚返回失败）：

```sql
-- ① 意向占位
UPDATE twelve_exchange_offer SET status='accepted', handle_time=NOW()
WHERE id=#{offerId} AND tenant_id=#{tid} AND status='pending';

-- ② A 物品锁定
UPDATE twelve_exchange_item SET status='locked'
WHERE id=#{itemId} AND tenant_id=#{tid} AND status='onswap' AND owner_id=#{ownerA};

-- ③ B 物品锁定（快照意向不可直接接受：item_b_id 为 NOT NULL，
--    service 层前置拦截 offer_item_id 为空的意向并提示"请对方发布物品后再接受"）
UPDATE twelve_exchange_item SET status='locked'
WHERE id=#{offerItemId} AND tenant_id=#{tid} AND status='onswap' AND owner_id=#{offerorId};
```

随后：生成订单（created）+ 两个面交码；该物品其余 `pending` 意向批量置 `rejected`（附系统备注），IM 通知 B 及被婉拒方。

### 4. 双边履约

- **面交**（社区场景默认）：订单页双方各自出示 6 位交换码核对身份/物品 → 各自点"我已交付" → 各自点"我已收到"
- **快递**：各自填运单号即视为交付，各自点"我已收到"
- 每个动作：条件 UPDATE（时间戳列为空才允许写）+ 落 `order_log` + IM 通知对方
- 双方都确认 → `completed`，双方物品 `swapped`，双方 `swap_count+1`

### 5. 取消 / 纠纷 / 超时

- **取消**：双方都未交付时任一方可取消（物品解锁回 onswap，IM 通知对方）；单方已交付后不可直接取消，只能走纠纷
- **纠纷**：任一方发起 `disputed`（填原因，可附聊天截图说明），物品保持 locked；后台 `/admin/exchange/order` 裁决：`force-complete`（按现状完成）或 `force-cancel`（取消并解锁），裁决结果写 `dispute_result` 并 IM 双方
- **超时任务**（`@Component("exchangeTask")`）：
  - `scanTimeoutOffer`（每 5 分钟）：pending offer 过期置 expired + 通知
  - `scanTimeoutOrder`（每小时）：created 超 7 天未双交付 → cancelled + 解锁 + 通知；pending_confirm 超 3 天未双确认 → 自动 completed（默认收货）
- **无资金流说明**：换物 MVP 不涉及支付托管，信任依赖——面交当面核验（主形态）+ 双向评价信用 + 后台裁决兜底。差价补偿、押金模式见"后续扩展"

### 6. 评价

- completed 后 14 天内双向评价（1-5 星 + 文字），`uk_order_reviewer` 防重复
- 评价立即展示在对方"换物主页"（复用用户主页模式，展示 swap_count、平均分）

## 八、关键设计细节

### 8.1 多租户隔离

- 所有表带 `tenant_id`，mapper 显式 `@Param("tenantId")`，由状态机经 `TenantContext` 注入（对齐 runner，不走自动拦截器）
- 异步通知线程无租户上下文，`ExchangeOrderNotifyEvent` 携带 tenantId 兜底（对齐 runner listener）

### 8.2 幂等与并发

- 接受意向、物品锁定、交付、确认全部走**条件 UPDATE 乐观锁**（`WHERE status/时间戳列符合预期`），影响行数=0 即业务失败，天然幂等防双击
- 订单号/物品号唯一索引兜底重复提交
- 面交码 `uk_order_side` 防重复生成

### 8.3 消息通知矩阵（IImService system 通道）

| 触发时机 | 通知对象 |
|----------|----------|
| 收到换物意向 | 物品主人 A |
| 意向被接受 / 被婉拒 / 过期 | 发起人 B（及被批量婉拒的其他发起人） |
| 订单建立 | 双方 |
| 对方已交付 / 对方已确认 | 对方 |
| 交换完成 | 双方 |
| 订单取消 / 超时取消 / 自动完成 | 双方 |
| 纠纷发起 / 裁决结果 | 双方 |
| 初审驳回 | 物品主人 |

### 8.4 反作弊与风控

- 不能对自己物品发起意向（后端强制）；同一物品同人仅一个 pending 意向
- 面交为主默认值（`delivery_mode` 默认 face），当面核验把无担保风险降到最低
- 单方已交付后不可单方取消——只能纠纷裁决，堵住"交付后反悔"漏洞
- 违约行为（超时取消、纠纷败诉）落 order_log，为二期信用分积累数据
- 内容安全：AI 初审 + 人工兜底（与商品/动态同一套体系）
- 首次发布可配置人工必审（租户级开关，二期）

### 8.5 与推荐/AI 的关系（MVP 边界）

- **MVP 零 AI 改动**：初审、估价全部复用现有 ai-service 端点；广场排序用 hot_score（热度=浏览+意向加权，同商品模式）
- **二期智能匹配**（解决以物换物"双重需求巧合"）：`want_desc`/`want_cats` 与物品文本都已在库，新增向量匹配端点（bge-m3 + FAISS，`recommend.py` 同模式）：我的 want_desc ↔ 全租户 onswap 物品相似度 + 类目过滤，产出"为你推荐的交换机会"与"有人想换你的东西"双向提醒

### 8.6 定时任务汇总（sys_job）

| Job | Cron | 逻辑 |
|-----|------|------|
| `exchangeAiModeration.auditItems` | `0 */10 * * * ?` | 扫 auditing 物品走 AI 初审三分流 |
| `exchangeTask.scanTimeoutOffer` | `0 */5 * * * ?` | pending 意向过期关闭 + 通知 |
| `exchangeTask.scanTimeoutOrder` | `0 0 * * * ?` | 建单 7 天未双交付取消；双交付后 3 天未双确认自动完成 |

## 九、风险点与缓解

| 风险 | 缓解方案 |
|------|----------|
| 双重需求巧合：租户内物品池小，匹配率低 | MVP 用"期望换什么"结构化字段+广场筛选兜底；二期向量匹配；`accept_any` 支持开放式交换 |
| 无资金担保，先交付方风险 | 面交为默认形态（社区场景天然适配）+ 交换码核验 + 单方交付后禁止单方取消 + 后台裁决 |
| 双边状态机复杂导致漏态 | 时间戳列建模双边进度、status 仅 6 个值；所有流转走统一状态机条件 UPDATE；order_log 全量可追溯 |
| 意向接受并发（两人同时被接受/同物品两意向同时成交） | 接受动作三步乐观锁事务，物品 locked 后其余意向必然失败 |
| 内容风险（违禁品换物） | 复用 AI 初审 + 人工审核 + 举报通道（复用现有举报体系） |
| 匹配冷启动（新租户空广场） | 类目运营位 + 管理后台可置顶推荐（hot_score 权重） |
