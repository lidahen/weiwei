# Weiwei 项目 AI 功能评估 — 哪些多余、哪些该深化

> 评估日期：2026-10-15。基于对 `ai-service/` 全部路由、services、agent 图、评测集的实际代码审读，非泛泛而谈。
>
> 结论先行：**平台化基建已经超配（网关/配额/多模型路由/Skill 热加载都有），但几个核心 agent 的"智能深度"和"质量度量"还停留在 MVP**。下一步该做减法 + 纵深，而不是加新功能。

## 二、多余 / 过度的部分（建议收缩）

### 1. AI 音乐（歌词/TTS/声音克隆）— 建议冻结
- 二手交易 + 跑腿场景里，音乐创作和主业**零协同**：不产生交易、不提升信任、不反哺推荐。
- 维护成本却不低：`music_vendor/` 第三方对接、声音克隆、`tests/music/`，一条完整的产品线。
- **建议**：代码保留但不迭代；如果计费账本显示长期无真实调用量，直接下线路由。

### 2. AI 创作工作台 — 建议收缩为"发布物料生成"
- 拆解/人设/分镜/渲染是一套**短视频博主工具**，和"社区二手交易"的用户画像不匹配。业主卖个旧沙发不需要生成分镜脚本。
- 但它里面的 **视频拆解 → 爆款模板（`ai_viral_template`）** 有一个有价值的用途：把商品文案 + 实拍图自动拼成" posting 视频/图文"，服务发布转化。
- **建议**：把"通用创作台"收缩为"卖货物料生成"（文案 + 图 + 可选短视频），其余入口收进管理后台或下线。

### 3. 首页小组件 645 行 — 投入产出失衡
- 天气 + 激励语写了 645 行（缓存、降级、时区、配额全都有），但业务价值只是首页一块装饰。
- 好的一面：它的降级设计（模板池兜底、永不报错）是教科书级的；坏的一面：为一句激励语花掉的价值远超 AI 初审之外任何核心功能。
- **建议**：冻结，不再迭代。别删——它的降级模式值得其他功能抄。

### 4. Prompt 增强 Skill 体系 — 用对了地方，但覆盖错了对象
- `skills/prompt-enhance`、`video-prompt-pro` 是给**图片/视频生成**服务的。而主业里最需要 prompt 工程化的导购 Agent 和初审，反而是硬编码 prompt。
- **建议**：把 Skill 热加载机制（`skill_loader.py`）用到导购 Agent 的意图路由 prompt 和初审 prompt 上——这才是它该服务的对象。

## 三、需要深化的部分（按优先级）

### P0：导购 Agent —— 从"路由器"进化成"顾问"

现状：LangGraph 意图路由 + 指代消解已经做了，评测集 26 条准确率 92.3%，基础扎实。但看 `router_cases.json` 就能发现深度缺口：

| 现状 | 深化方向 |
|---|---|
| 只做意图分类 + 工具调用，单轮找商品 | **多轮决策**：用户"买这个"时，Agent 应该先检查该商品的议价/纠纷状态、卖家活跃度，再决定引导下单还是提醒风险 |
| 工具返回什么就展示什么 | **结果融合**：商品列表 + 该用户的历史浏览/收藏/估价数据融合排序（你已经有六路召回推荐系统，Agent 检索结果和推荐系统是两张皮，接起来） |
| L2/L3 确认机制是两段式 MVP | 已经注释里写了"可平滑升级为 interrupt"——升级它，同时给 checkout 加"估价偏离提醒"（用户下单价明显高于 `valuation.py` 的 p50 时 Agent 主动提示） |

**为什么这是 P0**：这是你转型 agent 开发的核心作品。"估价 + 下单风险提示"这种带业务判断的 agent 行为，和"调个 API 返回结果"有本质区别，面试/简历上是两个物种。

### P1：评测体系 —— 从 1 个评测集到覆盖全部核心链路

现状：只有导购路由一个评测集（`agent_eval/`），26 条，手跑脚本。

深化三步：
1. **初审评测集**：初审是最适合评测的功能（有明确 ground truth：违禁/引流/正常）。构造 100 条标注样本（含图文），每次改 prompt/模型跑一遍，盯准确率 + 漏放率（漏放比误拒严重）。
2. **RAG 检索评测**：对知识库问答，准备 query → 应命中的 slice_id 评测集，量化召回率@k。现在 `rag_service.py` 还有 LIKE 降级路径，评测能告诉你降级时质量掉多少。
3. **进 CI**：评测脚本参数化（模型、prompt 版本），产出对比报告。这一步做完，你就有"AI 质量工程"的完整故事。

### P2：AI 估价 —— 最被低估的功能，值得做成招牌

现状：`valuation.py` 的设计理念非常好（"价格数字绝不来自 LLM"，纯统计 + 成色系数 + 样本不足如实标注）。但 172 行只覆盖了"给个区间"。

深化：
- **发布场景闭环**：识图填单 → 估价 → 文案 → 建议定价，串成一条"拍照即发布"流水线（目前四个功能是孤立的）
- **估价校准**：成交后回写"建议价 vs 成交价"偏差，统计 MAE，形成估价质量的自我度量
- **议价助手**：买卖双方议价时，Agent 用估价数据做中间参考（"该类目近 180 天成交中位数 ¥320，卖家要价 ¥450 高出 40%"）

### P3：知识库 RAG —— 明确服务对象再投入
现状：切片/索引/检索都有，但知识库在二手交易场景里**知识从哪来**不清晰（KB_5、KB_6 是什么内容决定了价值）。
- 如果是"平台规则/交易纠纷 FAQ"→ 深化它，接进导购 Agent 的 after_sales 意图，让售后咨询有据可答
- 如果只是随便传的文档 → 冻结，别在向量库选型（Milvus/pgvector）上花时间

### P4：社区日报 / 激励语 — 保持现状
功能没问题，但属于运营侧的锦上添花，不值得再投入。它们的降级设计已经足够好。

## 四、转型视角：这个项目还能给你什么

结合你"转 agent 开发"的目标，项目里已有的、面试值钱的素材：

| 素材 | 讲法 |
|---|---|
| L2/L3 工具分级 + 幂等键 + 跨租户直写缺陷的防御（`tools.py` 里那段 JavaInternalUnavailable 注释） | "我设计过 agent 工具的权限分级与资金安全机制，踩过跨租户数据泄漏的坑" |
| 估价"数字不来自 LLM"的设计 | "我知道 LLM 的边界，幻觉敏感场景用统计而非生成" |
| 全链路降级（FAISS→LIKE、LLM→模板池、视觉→纯文本） | "AI 功能的可用性工程：每个 AI 依赖都有非 AI 兜底" |
| 路由评测集 92.3% | "我建立了意图路由的回归评测" — 深化 P1 后升级为"我建立了全链路 AI 质量评测" |

**短板**（按 P1~P2 补）：评测覆盖、agent 多轮决策深度、质量自我校准。补齐这三块，"业务 Agent 落地"的定位就立住了。
