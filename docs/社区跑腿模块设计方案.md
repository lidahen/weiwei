## 一、整体业务流程

```
【用户 A】下单 → 【任务大厅】→ 【用户 B】接单 → 【执行】→ 【用户 A】确认 → 【资金流转】
    ↓              ↓             ↓             ↓           ↓            ↓
  发布       可见/接单       状态:已接单    配送中      待确认      付费→B收钱
  (免费/付费)                    ↓                            免费→B得积分
                            拒单/换人                        投诉→客服介入
```

**任务状态机：**

```
pending (待接单)
   ↓ 接单
accepted (已接单)
   ↓ 开始配送
running (配送中)
   ↓ 提交完成
pending_confirm (待下单人确认)
   ↓ 确认
completed (已完成)

异常分支：
pending → cancelled (超时未接单/用户取消，付费退款)
accepted → rejected (跑腿人拒单，回到 pending)
running → disputed (下单人发起投诉)
pending_confirm → refund (下单人申请退款，进入 CS 审核)
```

## 二、技术架构决策

| 方案 | 说明 | 推荐 |
|------|------|------|
| **A. 放在 `twelvet-trade` 里** | 跑腿是 C2C 交易的一种，复用现有支付网关 `WechatGateway`/`AlipayGateway`/`PaymentNotifyController` | ✅ 推荐 |
| B. 新建 `twelvet-runner` 独立模块 | 职责分离清晰，但需重建支付网关引用 | 后期规模大再拆 |

**决策**：走方案 A。跑腿本质是"小额服务交易"，与现有 trade 模块同源。

## 三、数据库表设计

### 表1：`twelve_runner_task`（跑腿任务）

```sql
CREATE TABLE `twelve_runner_task` (

  `assignee_id`     BIGINT        DEFAULT NULL COMMENT '接单跑腿人用户ID',

  `title`           VARCHAR(100)  NOT NULL COMMENT '任务标题',
  `description`     TEXT          COMMENT '详细描述',
  `pickup_addr`     VARCHAR(255)  COMMENT '取件/起点地址',
  `deliver_addr`    VARCHAR(255)  COMMENT '送达/终点地址',

  `deliver_lat`     DECIMAL(10,7) COMMENT '终点纬度',
  `deliver_lng`     DECIMAL(10,7) COMMENT '终点经度',
  `is_paid`         TINYINT       NOT NULL DEFAULT 1 COMMENT '1付费 0免费',
  `price`           DECIMAL(10,2) DEFAULT 0.00 COMMENT '报酬（元）',
  `bonus_amount`    INT           DEFAULT 0 COMMENT '免费任务的积分奖励数',
  `status`          VARCHAR(20)   NOT NULL DEFAULT 'pending' COMMENT '状态',
  `expect_time`     DATETIME      COMMENT '期望完成时间',
  `deadline`        DATETIME      NOT NULL COMMENT '接单截止时间',
  `assign_time`     DATETIME      COMMENT '接单时间',
  `finish_time`     DATETIME      COMMENT '完成时间',
  `confirm_time`    DATETIME      COMMENT '确认时间',

  `refund_status`   VARCHAR(20)   COMMENT '退款状态',
  `pay_order_id`    BIGINT        COMMENT '关联支付单ID',

  `finish_images`   VARCHAR(500)  COMMENT '完成凭证图片（JSON数组）',
  `create_by`       BIGINT,
  `create_time`     DATETIME      DEFAULT CURRENT_TIMESTAMP,
  `update_time`     DATETIME      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_task_no` (`tenant_id`, `task_no`),
  KEY `idx_tenant_status` (`tenant_id`, `status`),
  KEY `idx_publisher` (`tenant_id`, `publisher_id`),
  KEY `idx_assignee` (`tenant_id`, `assignee_id`),
  KEY `idx_deadline` (`tenant_id`, `deadline`),
  KEY `idx_task_type` (`tenant_id`, `task_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='跑腿任务表';
```

**状态值：**
- `pending` - 待接单
- `accepted` - 已接单
- `running` - 配送中
- `pending_confirm` - 待确认
- `completed` - 已完成
- `cancelled` - 已取消
- `disputed` - 有纠纷
- `refund` - 退款中

## 四、核心业务逻辑

### 1. 下单

- **免费任务**：仅落库，无需支付，`is_paid=0`，可配置积分奖励 `bonus_amount`
- **付费任务**：先创建 `PayOrder`（复用现有支付单），冻结下单人支付单，支付成功后 `status` 才允许跑腿人接单
- 生成 `task_no`：`RUN` + 时间戳(yyyyMMddHHmmss) + 6位随机数
- 落 `runner_task_log`（`action='publish'`）

### 2. 接单（**核心难点：并发抢单**）

**关键设计**：不能让两个用户同时抢到同一单。用**乐观锁 + 事务**：

```sql
-- 接单原子操作
UPDATE twelve_runner_task 
SET assignee_id = #{runnerId}, 
    status = 'accepted',
    assign_time = NOW(),
    update_time = NOW()
WHERE id = #{taskId} 
  AND tenant_id = #{tenantId}
  AND status = 'pending'
  AND deadline > NOW()
  AND publisher_id != #{runnerId};   -- 不能自己接自己
```

- 用 `UPDATE 影响行数 == 0` 判断"已被抢"
- 同步落 `runner_order` 表
- 落 `runner_task_log`（`action='assign'`）
- 通过 `twelvet-im` 推送下单人"您有新的跑腿接单"

### 3. 开始配送

- 跑腿人点击"开始配送"，`status: accepted → running`
- 记录开始时间，落日志

### 4. 提交完成

- 跑腿人上传完成凭证（图片/位置打卡）
- `status: running → pending_confirm`
- 落 `finish_images` 和 `finish_time`

### 5. 确认完成与资金流转

- **付费任务**：`pending_confirm → completed`，解冻 `PayOrder`，余额转入跑腿人账户
- **免费任务**：`pending_confirm → completed`，跑腿人账户 +X 积分（`bonus_amount`）
- **超时未确认**：定时任务 3 天后自动确认（`confirm_time` 补填）

### 6. 超时未接单

- 定时任务 `RunnerTaskTimeoutJob` 扫描：`status='pending' AND deadline < NOW()`
- 付费任务：触发退款，`status → cancelled`
- 免费任务：直接 `status → cancelled`
- 通知下单人

### 7. 投诉/纠纷

- 下单人可在 `running` 或 `pending_confirm` 阶段发起 `disputed`
- 创建 CS 工单（复用 `CsDisputeService`）
- 客服介入，可强制退款/补偿

## 八、关键设计细节

### 8.1 多租户隔离

- 所有表带 `tenant_id`
- 实体继承 `BaseEntity`（`framework-core` 里已有）
- DAO 层通过 `TenantBindInterceptor` 自动注入租户上下文
- 所有接口路径无需带租户前缀，由拦截器从 Session 解析

### 8.2 幂等性

- 接单接口用 `assign_no` 幂等键（防止双击接单）
- 支付回调复用现有 `PaymentNotifyController` 的幂等机制
- 状态流转用乐观锁 UPDATE，天然幂等

### 8.3 消息通知

| 触发时机 | 通知对象 | 通道 |
|----------|----------|------|
| 新任务发布 | 附近跑腿人（半径 3km） | IM + 站内推送 |
| 接单成功 | 下单人 | IM + 短信（可选） |
| 任务完成 | 下单人 | IM |
| 超时提醒 | 下单人 | IM |
| 退款到账 | 下单人 | IM |

### 8.4 反作弊

- 自己不能接自己下的任务（后端强制校验）
- 完成凭证：拍照上传 + 位置打卡（距离过远自动拦截）
- 起点到定位点超过 X 公里自动拦截（默认 200m）
- 同一 IP 短时间内多次接单异常监控
- 首单需人工审核（可选）
- 按跑腿人信誉权重排序大厅任务

### 8.5 支付与资金流

```
下单人支付 → 支付单冻结（挂账）
       ↓
    接单
       ↓
   配送中
       ↓
  提交完成
       ↓
   待确认 ← 下单人发起退款 → 进入 CS 审核
       ↓
   确认完成
       ↓
支付单解冻 → 资金转入跑腿人余额账户
```

- **付费任务**：复用 `PayOrder` + `PaymentNotifyController`，无需新建支付逻辑
- **免费任务**：下单时无需支付，任务确认后 `bonus_amount` 转为跑腿人积分

### 8.6 定时任务（`twelvet-quartz`）

| Job | Cron | 逻辑 |
|-----|------|------|
| `RunnerTaskTimeoutJob` | `0 */5 * * * ?` | 扫超时未接单 → 取消+退款 |
| `RunnerAutoConfirmJob` | `0 0 0/1 * * ?` | 扫超时未确认（3 天）→ 自动完成 |
| `RunnerDailyIncomeJob` | `0 0 1 * * ?` | 每日 1 点结算跑腿人收益到余额 |

## 九、风险点与缓解

| 风险 | 缓解方案 |
|------|----------|
| 抢单并发冲突 | 乐观锁 UPDATE，失败返回"已被抢" |
| 接单后跑单 | 支付单冻结，任务完成前不下发资金 |
| 定位作弊 | 起点/终点双定位打卡 + 距离校验 |
| 任务欺诈 | 首单人工审核（可选）+ 按信誉权重 |
| 免费任务薅羊毛 | 每日免费接单次数限制（如 3 次/天） |
| 恶意退款 | 完成凭证 + 客服审核 + 信誉扣分 |
| 支付回调丢失 | 定时任务对账（复用现有支付对账机制） |
