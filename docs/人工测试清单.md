### 0.4 数据库检查约定（资金类项目的主要判据）

> 以下查询的**列名已逐一对库核实**，可直接粘贴执行（`out_trade_no` 就是页面/接口上的 `payNo`）。

```bash
MYSQL="/f/MySQL/MySQL Server/bin/mysql -uroot -p123456 -D twelvet-fast --default-character-set=utf8mb4"

# 支付单（biz_type 是本轮核心：trade=商品 runner=互助 renew=续费）
# 注意：退款金额不在本表，看 trade_refund.amount
$MYSQL -e "SELECT out_trade_no, biz_type, order_id, status, pay_amount, paid_at FROM trade_pay ORDER BY pay_id DESC LIMIT 10;"

# 商品订单（状态与三个时间点：支付 / 发货 / 完成；本表没有 pay_status 列）
$MYSQL -e "SELECT order_id, order_no, status, total_amount, paid_at, shipped_at, done_at FROM trade_order ORDER BY order_id DESC LIMIT 10;"

# 退款单（amount = 退款金额，status + active_flag 决定是否还在进行中）
$MYSQL -e "SELECT refund_id, order_id, type, amount, status, active_flag FROM trade_refund ORDER BY refund_id DESC LIMIT 10;"

# 结算单（金额三列：gross 商品总额 / commission 佣金 / net 卖家实得；hold_until 为持有截止）
$MYSQL -e "SELECT settlement_id, order_id, seller_id, status, gross_amount, commission_amount, net_amount, hold_until FROM settlement_order ORDER BY settlement_id DESC LIMIT 10;"

# 卖家账户与资金流水（flow 的 type + amount + balance_after 是核对余额的关键）
$MYSQL -e "SELECT account_id, seller_id, kyc_status, balance, frozen FROM seller_account;"
$MYSQL -e "SELECT flow_id, seller_id, type, amount, balance_after, settlement_id, withdraw_id, create_time FROM seller_balance_flow ORDER BY flow_id DESC LIMIT 10;"

# 互助任务（pay_status 在本表：unpaid / paid / refunded）
$MYSQL -e "SELECT id, task_no, status, is_paid, price, pay_status, pay_out_trade_no FROM twelve_runner_task ORDER BY id DESC LIMIT 10;"
```

## 1. 商品交易 + 支付闭环

> 自动化已覆盖：支付单创建、状态机迁移、结算单创建。人工补的是**跨进程真实链路**与**迟到支付时序**。

### [P0] 1.1 正常下单 → 支付 → 发货 → 收货 → 结算单生成

1. 用 `user_demo` 登录，在首页挑一件 `seller_demo` 的商品 → 详情页 → 立即购买 → 结算页确认地址 → 提交订单
2. 订单详情页发起支付 → 选择支付宝/微信 → 跳收银台拿到支付单号
3. **此时先不支付**，查库确认支付单为 `unpaid`、订单为 `unpaid`
4. 支付（收银台 mock 按钮，或直接调 `POST /payment/mock-pay/{payNo}`）

**预期**：

- 支付单 `status='paid'`，`biz_type='trade'`
- 订单 `status` 从 `unpaid` → **`unshipped`**（已支付待发货），**且订单不消失、不重复**
  （订单状态取值：`unpaid` → `unshipped` → `shipped` → `done`；取消或超时 → `closed`）
- 卖家侧订单可见该单，可发货（填运单号）
- 买家确认收货后：订单 `status='done'`、`done_at` 有值
- **结算单自动创建**：`settlement_order` 出现一行，`status='holding'`、金额 = 商品实付

**关注点**：收货瞬间是否**恰好生成一行**结算单（重复生成 = 重复结算）。

### [P0] 1.2 迟到支付 → 自动原路退款（不复活订单）

这是 `biz_type` 收口最关键的一条，必须在真实链路验一次。

1. 新建一笔订单并进入支付页（拿到 `payNo`）
2. **不支付**，等订单超时关闭（或把 `trade_order` 的 `expire_at` 改成过去，再手动执行超时关单任务）
3. 确认订单已 `closed`、支付单仍 `unpaid`
4. 在**订单已关闭之后**调 `POST /payment/mock-pay/{payNo}`

**预期**：

- 订单**保持 `closed`，绝不复活**
- 支付单**先变 paid，随即自动变 refunded**（退款金额看 `trade_refund.amount`，`trade_pay` 表本身不存退款金额）
- 买家收到一条"订单已关闭，自动退款"的系统通知
- 后端日志出现：`[支付] 迟到支付：订单已 closed，自动原路退款`

### [P1] 1.3 订单未支付时的取消

1. 下单后不支付，主动取消订单

**预期**：订单 `closed`；该订单**没有**生成结算单；支付单（若已创建）`status` 不为 paid。

### [P1] 1.4 续费支付不串台（`biz_type='renew'`）

1. `admin` 登录 → 租户管理 → 选一个租户 → 续费 → 生成支付单
2. `POST /payment/tenant-renew/mock-pay/{payNo}`

**预期**：支付单 `biz_type='renew'`、`order_id` 为空；**不产生**任何商品订单状态变化，也不生成结算单。

## 2. 退款售后

> 自动化已覆盖：退款状态机、互斥规则。人工补的是页面流转与"钱和库存是否真的回去了"。

### [P0] 2.1 未发货退款（仅退款）

1. `user_demo` 对一笔已支付未发货订单发起退款（`/trade/refund/apply?orderId=...`，原因填中文以便验证编码）
2. 卖家侧同意 → 买家侧确认

**预期**：

- 退款单走完流程后，`trade_pay.status='refunded'`，`trade_refund.amount` = 退款金额且与实际支付一致
- 订单终态为 `closed`
- **结算单**：未收货的单原本就没有结算单（不应凭空生成）；**若已存在 `holding` 结算单（收货后退款的情形），必须被置为 `closed`，绝不能继续进入解冻**——这是资损点，务必查库确认

### [P1] 2.2 已发货退款（退货退款）

1. 卖家发货后买家申请退货退款 → 卖家同意 → 买家填退货物流 → 卖家确认收货退款

**预期**：全链路页面状态与文案正确；退款完成后订单不再出现在"待收货"。

### [P1] 2.3 客服介入

1. 卖家拒绝退款 → 买家申请平台介入 → `cs_demo` 登录处理

**预期**：客服侧能看到完整时间线（`RefundTimeline`），处理结果对双方可见。

### [P0] 2.4 已结算订单的售后退款 → 扣回（clawback）

> 这条必须做：它走的是"钱已经打给卖家了，又发生退款"的路径，**唯一会扣卖家余额的地方**。

1. 先按 4.2 / 4.3 把某笔订单的结算推到 `settled`（卖家余额已增加）
2. 买家对该订单发起售后退款（订单已是 `done`）→ 卖家同意 → 退款成功

**预期**：

- 结算单 `settled` → `clawback`
- `seller_balance_flow` 新增一条 **`type=clawback`、金额为负** 的流水，`balance_after` = 扣回后余额
- **同一笔退款重复触发不会扣两次**（幂等键 `clawback:{refundId}`）
- 若扣回后余额为负 → 卖家账户被**冻结**（`seller_account.frozen=1`），卖家侧提现被拒

### [P2] 2.5 中文原因与超长文本

退款原因 / 留言填中文 + 200 字长文本提交。

**预期**：详情页展示无乱码、无截断。

## 4. 结算账本（运营 + 卖家中心）

> 这是本轮最需要人工过一遍的模块：金额、流向、审核动作是否与运营直觉一致。

### [P0] 4.1 卖家实名（KYC）

1. `seller_demo` → 卖家中心 `/user/settlement` → 提交实名资料（姓名/身份证/银行卡/开户行）
2. `admin` → 后台 运营管理 → **实名审核** `/admin/marketplace/kyc` → 通过

**预期**：

- 后台列表**脱敏展示**证件与卡号（不是明文）
- 审核通过后，卖家中心显示"可提现余额"，且该卖家的 `holding` 结算单才有资格进入下一步
- 审核**未通过**的卖家：结算单**不会被推进**（这是校验点，可故意测一次）

### [P0] 4.2 到期解冻：holding → pending_settle

前置：有 `done` 且过了 7 天的订单 + 卖家 KYC 已通过。

1. 改库把 `trade_order.done_at` 设为 8 天前（见 0.5）
2. 手动执行 `settlementScan.scan`
3. 后台 → 运营管理 → **结算单** `/admin/marketplace/settlement`

**预期**：

- 该结算单 `holding` → `pending_settle`
- 金额不变、卖家正确、租户正确
- **有进行中退款的订单不会被推进**（可用 2.1 造一个进行中退款对照）
- **KYC 未通过的卖家不会被推进**

### [P0] 4.3 打款：pending_settle → settled

1. 手动执行 `settlementPayout.payout`

**预期**：结算单 → `settled`；卖家账户余额增加；`seller_balance_flow` 增加一条**对应金额**的流水（金额对得上，方向正确）。

### [P0] 4.4 提现申请 → 审核 → 凭证

1. `seller_demo` 卖家中心 → 申请提现（金额不超过可提现余额）→ 提现单为 `pending`
2. `admin` → 运营管理 → **提现审核** `/admin/marketplace/withdraw` → **审核通过**（`approved`）
3. 同页 **打款**：填线下打款凭证 → 提现单变 `paid`

**预期**：

- 申请时余额被扣减/冻结，**不能申请超过可提现余额的金额**
- 审核步骤可"驳回"（`rejected`），驳回后余额应退回
- **打款凭证为必填**（后端硬校验，空凭证直接报"请上传打款凭证"）
- 打款完成后卖家侧提现记录可见、状态正确，`seller_balance_flow` 有对应出账流水

### [P1] 4.5 对账差异

> ⚠️ 对账对象是 **T-1（昨天）业务日**，不是"今天刚做的事"——今天的交易要明天才会被扫到。手工执行时看日志里的 `bizDate=`。

1. 账平时手动执行 `settlementRecon.reconcile` → 预期 `diffs=0`
2. **人为制造差异**：改掉某一行资金流水的金额（不改余额），再执行同一任务
3. 查后台 **结算对账** `/admin/marketplace/recon` 与 `settlement_recon_diff` 表

```bash
# 制造"账本漂移"：让流水合计与账户余额对不上（ledger 类差异）
$MYSQL -e "UPDATE seller_balance_flow SET amount = amount + 1 WHERE flow_id = <某条流水ID>;"
```

**预期**：

- 账平时零差异；制造后能识别为差异（**而不是静默通过**）
- 差异表能看到类型（`missing` 有单无结算 / `phantom` 有结算无单 / `amount` 金额不符 / `status` 退款状态不符 / `duplicate` 重复结算 / `ledger` 账本漂移）

### [P1] 4.6 解冻只作用于已 resolve 的行

造一个"结算单已 holding、退款后来又 resolve（关闭）"的场景再执行解冻。

**预期**：解冻**只对最终 resolve 的结算单生效**，不适用于仍有争议/进行中退款的单。
