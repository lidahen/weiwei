ROUND 3 · HITL & INTELLIGENCE

weiwei Agent 改进报告（第 3 轮）：敏感操作人机协作 + 智能度实证优化

对象：ai-service/app/services/agent/ · 触发：用户反馈「结果不符合预期 + 支付/退款应由人操作」 · 日期：2026-10-10

两个诉求分别用实证数据和HITL 红线解决：智能度问题不再靠猜——用第 2 轮建好的评测集真实跑分定位失败模式，按证据修 prompt 后复测 88.5% → 96.2%；敏感操作按「资金红线由人执行」重构工具边界。

一、HITL：支付/退款等敏感操作由人执行

操作改前改后（人机分工）
支付 agent 持有 pay_order 工具，确认后直接把订单标为已支付（模拟扣款） 工具移除pay_order 从 Agent 工具注册表移除（函数保留供测试与未来支付回调）。下单成功后由话术引导用户本人到「我的-订单」页完成支付。系统提示词新增第 11 条红线：绝不能声称"已为你支付"。
退款/退货 agent 可提交纠纷工单（工单本就流转人工仲裁） 边界明确保留 create_dispute（提交工单=转人工），但提示词明确：退款由平台客服人工审核处理，agent 不得承诺退款金额或到账时间。
下单（confirm_order） 两段式确认 + 幂等键 不变。创建未支付订单不转移资金，保留在 agent 能力内；支付环节交还用户。

改动文件：tools.py（注册表）、nodes.py（GUIDE_SYSTEM_PROMPT 第 11 条、状态标签）。SSE 协议不变，前端与 Java 侧无需改动。

二、智能度：用评测集实证定位并修复

对 26 条路由用例做真实 LLM 调用（两轮全量，各约 12–16 分钟），拿到第一手失败证据：

轮次准确率失败用例与归因
基线88.5%（23/26） R15 货不对板无"退款"字样→误判 other（售后描述缺关键词）；R24 "那个东西怎么样"→强行分发（缺模糊判定规则）；R26 无关话题→other 而非闲聊（闲聊定义过窄）。
修后92.3%（24/26） 首轮 3 个失败全部修复。剩 R09（订单/物流双关，属用例设计问题，已加 expected_any 双可接受）、R26（意图正确但置信度 0，模型波动）。
判定口径修正后96.2%（25/26）唯一遗留：闲聊类偶发低置信度→进澄清而非闲聊回复（体验瑕疵，无资金风险），记录观察。

路由 prompt 修复内容（ROUTER_SYSTEM_PROMPT）：

  • 售后定义补齐：与描述不符、质量问题、疑似假货、卖家不理人均归 after_sales（不依赖"退款"字样）；
  • 模糊判定规则：指代词在历史中找不到确定对象 → 归 other 低置信度；
  • 闲聊定义放宽：一切与购物/社区无关的话题（软件使用、生活求助、常识问答等）。

方法论价值：这正是路线图"评测先行"的闭环——不猜问题，先跑分、按失败分类修、修完复测验证。今后任何路由 prompt 改动都必须先过评测集（基线 ≥85%）。

三、补充：超时 / 死循环等异常场景加固（用户新增诉求）

审计结论——已有：LLM 调用超时 60s + SDK 重试 1 次、工具循环上限 5 步、上下文/结果截断、Redis 与 RAG 熔断降级。缺失并已补齐：

风险场景补强措施实现
单次工具卡死（DB/外部调用挂起）→ 长时间无回答工具级超时_invoke_tool_with_timeout：agent_tool_timeout（默认 20s）内未完成即返回结构化错误 JSON，模型可自行调整（换工具/如实告知），绝不挂死对话。超时计入 trace。
整图执行卡死 → SSE 无限挂起整图总超时 + 看门狗同步与流式路径均套 agent_graph_timeout（默认 120s）：同步路径超时返回兜底回复；流式路径看门狗取消任务并下发 error 事件，前端不再无限等待。
图执行死循环recursion_limit 显式化runner config 显式携带 agent_recursion_limit（默认 30，设计文档 6.6 要求放 config，此前遗漏）。
工具循环跑满 5 步未收敛耗尽兜底文案循环耗尽且模型仍未产出文本时，回复明确的「处理不顺利，可换个问法或转人工」，并在 trace 标记 loop_exhausted 便于统计该失败模式频率。
新增 tests/test_agent_resilience.py（4 条：慢工具超时返回错误 / 正常工具直通 / 整图超时兜底 / config 携带 recursion_limit）；全量 agent 回归 62 passed, 1 skipped（含 2 条旧断言按 recursion_limit 新增同步更新）。

三·补：上下文膨胀改「提炼总结」而非硬裁剪（用户新增诉求）

原状——历史超长时 _trim_for_llm 直接丢弃前缀消息（硬裁剪），用户早期需求/决定（商品 ID、地址、金额）会静默丢失。改造——滚动增量摘要：

机制说明
触发阈值state 消息数 > COMPACT_TRIGGER(24) 时触发；最近 COMPACT_KEEP_RECENT(12) 条保持原文不摘要（工具循环实时可见）。
增量提炼只把「已摘要覆盖点 → 切点」的新增段交给 LLM 压缩为要点列表（SUMMARIZE_SYSTEM_PROMPT 强制保留商品 ID/订单号/金额/地址/已确认决定），与旧摘要滚动合并——长对话只付一次增量成本，不重复摘要全量。
切点对齐切点从 HumanMessage 起切，保证 AI(tool_calls)→ToolMessage 序列不被拆散。
持久化摘要与覆盖位置写入 state（history_summary / summary_upto），随 checkpoint 跨轮保留；下轮若无足够新增段，直接用已有摘要重建 head，不耗 LLM 调用。
降级链LLM 摘要失败 → 朴素拼接尾部 6 条（_fallback_summary），再不行 → 原有 _trim_for_llm 兜底；摘要环节绝不阻断主流程。
新增 tests/test_agent_compact.py（10 条：阈值不触发 / 增量段正确 / 二轮滚动增量 / 无新增段不耗 LLM 重建 / 工具序列不拆散 / System·Tool 消息不入摘要 / LLM 失败降级 / fallback 边界）。全量 agent 回归 72 passed, 1 skipped。

四、验收结果

agent 相关测试全绿：test_agent + test_agent_polish + test_redis_persistence（补装 fakeredis）+ test_agent_eval + test_agent_resilience + test_agent_compact 共 72 passed, 1 skipped；在线评测两轮完成并落盘报告（tests/agent_eval/report_20261010_*.json，路由准确率 88.5% → 96.2%）；评测脚本新增 expected_any 多可接受意图支持并通过离线校验。

五、第二轮审计：修复 3 个严重缺陷（同日追查）

对压缩链路与编排做整体复审，发现并修复 3 个「写了但没生效 / 生效在错误地方」的缺陷：

缺陷严重度说明与修复
域人设从未生效严重runner 兼容路径注入旧版 4 条规则的 SYSTEM_PROMPT 占据 messages[0]，nodes 判断「已是 SystemMessage 则保留」恒真 → GUIDE/BUTLER 人设（含 HITL 红线第 11 条、下单 7 步流程）是死代码。修复：新增 _ensure_persona，每轮按域重建人设并附着 RAG；保留原消息 id，避免 add_messages 把新对象追加到历史末尾（旧 RAG 分支正有此隐患）。
摘要文本泄漏到用户流严重摘要压缩调用走 ainvoke_or_stream，流式模式下 token 汇会把摘要要点当作回答增量推给前端。修复：内部压缩直连 llm.ainvoke 并加 15s 超时（顺带补上摘要环节此前缺失的超时保护，卡死时降级 fallback）。
摘要被裁剪链路裁掉严重_trim_for_llm 只保留首条 SystemMessage，而历史摘要恰是第 2 条、且只在长历史场景生成——机制自己拆自己的台。修复：保留开头连续 SystemMessage（人设 + 摘要）。
新增 7 条回归测试（trim 双 System / persona 覆盖与 id 保留 / RAG 附着 / 无 System 前插 / 摘要不进 sink / 摘要超时降级），全量 agent 回归 79 passed, 1 skipped。

六、遗留与建议

项状态说明
闲聊偶发低置信度（R26 型）观察意图正确但 conf<0.6 会进澄清。若后续日志频发，可对 chitchat 单独放宽阈值或二次判类。
真实失败样本收集建议「结果不符合预期」若还指回答质量（非路由），请提供 1–2 条真实对话（session_id 或截图），用 trace 日志定位到具体环节后针对性修复。
支付页面跳转建议当前引导话术为文字描述；后续可让 confirm_order 返回携带 order_no 的前端可点击支付链接，进一步缩短路径。
看门狗触发时 trace 不落盘低chat_stream 超时取消任务时 result 不可得，只有 error 日志无结构化 trace；超时恰是最需观测的场景，后续可在 watchdog 里补一条轻量 trace。
客户端断开后后台任务跑完低SSE 连接断开时图任务继续执行至结束，浪费 token 但无正确性影响；可在 generator finally 里 task.cancel()。
