# 改进方向落地分析：技术投入 vs 战略优先级

> **2026-10-27 注**：本文引用的 2026-10-21 之前 SQL 初始化脚本已于 2026-10-27 清理；
> 相关表结构已并入 [docs/db 全量基线](db/twelvet-fast_2026-10-21.sql)，新环境按 README 基线导入。

> 输入：[docs/strategy/改进方向.md](strategy/改进方向.md)（自营 vs SaaS 战略判断）
> 方法：把文档的"阶段一必须做到的"逐条对照代码库现状，实测取证
> 结论一句话：**平台已经在准备"卖给物业"，但还没准备好"自己运营一个小区"。**

---

## 一、文档结论，翻译成技术要求

《改进方向》的核心判断是：**自营优先，SaaS 后置**。理由是社区二手交易的命门是"密度"和"运营"，不是软件。

阶段一（0-6 个月）要做三件事：

1. 选 1-3 个小区/园区，**亲手把交易闭环跑通**
2. **验证五个指标**：发布量、成交量、履约率、复购率、纠纷率
3. 打磨产品：小程序、认证、信用分、求购、推荐权重

那么阶段一的技术投入应该集中在三类能力：

| 类别 | 为什么阶段一需要它 |
|---|---|
| **可度量** | 五个指标看不见，就等于没在自营——你无法判断"一个小区到底转起来没有" |
| **信任** | 自营的壁垒是"亲自做认证、信用、纠纷仲裁"建立的真实信任 |
| **供需密度** | 求购是反向需求；只有卖没有求，冷启动永远缺半边 |

**而不是** SaaS 化（多租户售卖、计费、白标）。

## 二、关键发现：现有技术投入与战略方向错位

把已交付的功能按"服务哪个阶段"归类：

| 已交付能力 | 实际服务阶段 |
|---|---|
| 租户体系 5 轮（MVP → 跨 N 租户 → 子域名 → 角色菜单租户化） | 阶段二 / 三 |
| 商业化 3 轮（计费 MVP → 扫码续费支付闭环 → 过期降级） | 阶段二 / 三 |
| 支付渠道对接、套餐配额、AI 用量计费账本 | 阶段二 / 三 |
| 推荐系统、AI 全套能力、社区日报 | 阶段一（✅ 对口） |
| 跑腿互助 | 阶段一（✅ 对口） |

而文档点名属于**阶段一**的能力，现状是：

- **认证** —— 完全没有
- **信用分** —— 只覆盖跑腿员，二手卖家没有
- **求购** —— 完全没有

阶段一用来"验证模式"的五个指标，**只有一个现在能看见**。

这个错位不是"做错了"，而是**顺序**问题：SaaS 化的地基已经打得比产品价值验证还早。文档的建议恰好是把这个顺序掰回来。

## 三、逐项差距审计（实测取证）

### 3.1 阶段一产品能力

| 文档要求 | 状态 | 证据 |
|---|---|---|
| 小程序 | ❌ **完全没有** | 无 `weapp`/`miniprogram` 目录；`ui/` 是 Umi Max 4 H5 |
| 认证 | ❌ **完全没有** | `weiwei(1).sql` 的 `sys_user`（:2016）只有 RuoYi 标准字段，无 `real_name`/`id_card`/认证状态任何列；无申请-审核流程、无认证审核页 |
| 信用分 | ⚠️ **只覆盖一半** | 跑腿员完整：`RunnerCreditController` + `RunnerReviewServiceImpl.creditProfile()`（:127-165，公式 `avgRating*20*(0.7+0.3*完成率) - 5*异常单数`）。**二手卖家无独立信用分**，推荐打分里的 `sellerGoodRate`（`RecommendScorer.java:31`）只是好评率、权重 0.05，无加分/扣分闭环、无页面 |
| 求购 | ❌ **完全没有** | 无求购表 / 接口 / 页面；无供需匹配或撮合通知 |
| 推荐权重调整 | ⚠️ **可配但无界面** | 权重从 `application.yml` 的 `recommend.weights.*` 注入（`RecommendScorer.java:19,63-78`），A/B 组可覆盖；但没有任何管理端表单，改权重=改配置文件+重启 |

### 3.2 阶段一验证指标

| 指标 | 看板现状 | 数据可得性 |
|---|---|---|
| 发布量 | ❌ 无 | ✅ `product.publish_time`（:933）可算历史发布量 |
| 成交量 | ✅ 有（总订单数 + 7 日趋势） | — |
| 履约率 | ❌ 无 | ✅ `trade_order.status` / `done_at` / `shipped_at`（:2224-2230） |
| 复购率 | ❌ 无 | ✅ `trade_order.buyer_id`（:2213）可分组 |
| 纠纷率 | ⚠️ 只有计数，无比率 | ✅ `trade_dispute`（:2138）+ `trade_order` 可算 |

**结论：五个指标里只有 1 个能看见，另外 4 个数据都在库里、纯粹是没人查。**

## 四、意外发现：运营后台存在真实的数据越权（与战略无关，但应立即修）

审计过程中发现 `AdminMarketplaceMapper.xml`（运营后台全部统计/列表 SQL）**既没有租户过滤，也缺少鉴权注解**：

| 问题 | 证据 |
|---|---|
| 整个 mapper **0 处** `tenant_id` | `AdminMarketplaceMapper.xml` 全文无 `tenant_id`；同项目其它 mapper 有过滤（`ProductMapper.xml` 出现 20 次，全 backend 27 个 XML 有） |
| 统计 SQL 跨租户聚合 | `selectDashboardStats`（:7-17）的 `totalUsers`/`totalOrders`/`gmv`/`pendingDisputes` 全是全表子查询 |
| 商品/用户/举报列表跨租户 | `selectProductAuditList`（:37）、`selectReportList`（:77）、`selectUserList`（:91）均无租户条件 |
| **跨租户写**（IDOR） | `approveProduct`（:67）、`rejectProduct`（:72）是 `UPDATE product ... WHERE product_id = #{productId}`，无租户条件 → 可改他人租户商品状态 |
| 接口无权限校验 | `AdminMarketplaceController.overview()`（:38-46）没有 `@SaCheckPermission`（类里已 import 该注解） |

> 可对照：`product` 与 `trade_order` **都已加** `tenant_id` 列（`backend/data/neighborswap.sql:817` / `:825`），字段是现成的，只是这个 mapper 一个都没用。

**影响**：任何登录用户即可读取全平台经营数据；租户管理员在 `/admin/marketplace` 看到的是别人的数据，且能对别人的商品做审核动作。

## 五、优化优先级

### P0 —— 立即做

**1. 自营运营看板：补齐 5 个指标 + 修复上面的租户隔离/鉴权**

这是阶段一唯一能"看见"闭环的仪器。选它的理由：

- 数据 100% 已在库中，**纯读、零数据迁移、零新表**
- 顺手堵掉一个真实越权 + 跨租户漏洞
- 改动集中在 4 个文件：`AdminMarketplaceMapper.xml` / `IAdminMarketplaceService(+Impl)` / `AdminMarketplaceController` / `ui/.../admin/Dashboard.tsx`

### P1 —— 阶段一产品内核

**2. 卖家信用分体系** —— 直接复用跑腿员那套已验证的做法（可解释公式 + 实时聚合 + 展示 + 扣分闭环），数据源现成（`trade_review` / `trade_order`）。文档明确把"信用"列为自营的壁垒。

**3. 求购（反向需求）** —— 指向"供需密度"这个命门。你需要：求购表 + 发布/列表/详情 + **与在售商品的匹配通知**（有人卖 X 时通知求购者），后者才是价值所在。

### P2 —— 有余力再做

**4. 用户认证**（实名/业主认证 + 申请-审核流）—— 涉及身份证等敏感信息，动手前要先定合规口径与脱敏方案。
**5. 推荐权重管理端调参**（把 yml 搬上后台）—— 小改动，但能让你在不重启、不发版的情况下试权重，对阶段一"调推荐"很有用。

### 不建议现在做

**6. 微信小程序** —— 等于重写整个前端。阶段一用 H5 已足够验证"一个小区能不能转起来"；等阶段二确认模式可复制，再投入小程序。

**7. 更多 SaaS 化能力**（白标、租户自助开通、客户成功体系）—— 文档明确说后置。

---

## 六、建议的第一刀

**P0 的「自营运营看板」**。它是阶段一验证闭环的唯一仪器，且是所有选项里风险最低、见效最快的。

拟交付内容：

- **指标**：发布量（今日 / 近 7 日 / 趋势）、成交量 + GMV、履约率（含超时未发货）、复购率（窗口内下单 ≥2 次买家占比）、纠纷率（纠纷单 / 订单数）
- **窗口**：7 / 30 / 90 天可切换
- **维度**：严格按当前租户上下文过滤
- **安全**：补 `@SaCheckPermission` + mapper 全量补 `tenant_id`
- **兼容**：保留现有卡片（用户数/在售/待审/待仲裁），新增指标并列展示，不改动既有接口路径
